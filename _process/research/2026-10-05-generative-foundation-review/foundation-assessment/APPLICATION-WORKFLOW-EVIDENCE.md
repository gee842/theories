## The application distinction to preserve

Let `v0` identify the actual input code, result, checker, contract and source versions. These labels identify artifacts, not an authoritative ground-status oracle.

1. **Diagnostic obligation D(v0):** if requested by the owner, provide a complete independent audit record for `v0` in the designated accessible location. A successfully emitted bound report can satisfy this obligation even when it reports a semantic failure. Merely proposing to run the checker cannot.
2. **Correction obligation R:** the independently supported contract violation remains after D(v0) is satisfied. Creating an accurate failure report does not remove the defect. Current authorization controls whether the worker may repair it; withdrawal does not make the finding false or the unresolved maintenance issue disappear.
3. **Verification obligation D(v1):** an actual authorized code change and producer run generate a different code/result pair. The old audit remains evidence about `v0`, not verification of `v1`. A fresh independent check is now relevant. Stopping all verification because “the report already exists” is the opposite error from treating D(v0) as perpetually unfinished.

D and R have different fulfillment conditions; the same event need not satisfy both. They are operationally independent obligations, although diagnosis can supply evidence supporting repair. The worker should infer their status from the requested deliverables, actual versioned artifacts and observed effects. This does not require inventing a synthetic patient or giving it an evaluator's desired utility.

Saving the report can count as delivery only if the owner prospectively designates that local artifact as the deliverable. It does not prove a human read it. Repeating an unchanged verification is not inherently unethical; any restriction on redundant work must follow the actual task/resource contract. A genuine later input change can warrant another verification.
