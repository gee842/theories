## 2. Derive effects from executed writes

The inherited configuration has a control-arrangement field and a current response-exposure field. The latter has six codes: no exposed root, or one of five represented roots. A program is any finite list of writes to these fields. Their sequential semantics are explicit; the last write to a field determines that field's resulting value. Requests to erase records, forge the possibility list, replace the command installation or grant both ordinary write rights are also represented, but are denied by `commit` under every ordinary rights assignment.

The interpreter calculates the change class from the program's field footprint: no field gives `steady`, fault only gives `mobile`, control only gives `control`, and both give `reset`. `executed_writes_fit_derived_effect` proves, for every finite program and represented starting configuration, that its result is admitted by this class. ## 3. Permissions, recording and consumption

A packet binds the current configuration generation. A commit first checks that generation, all requested field rights and the inherited change permission. It then reserves one declared unit per listed write plus one for committing the record. On success it installs the transformed configuration and possibilities, appends the derived temporal change and a program journal entry, and increments the configuration generation. A denied or unaffordable commit exposes no partially transformed state in this specification.

The command installation keeps its root and mandate. Its serial and authority epoch advance; prior signing, issuing, delivery and completion flags are cleared. `old_command_request_is_revoked` proves that a request fresh before the commit is stale afterward. `replayed_packet_rejected` proves rejection of the same patch after it commits once. Configuration generation and command serial have distinct roles: reads do not advance configuration generation, and a successful command advances its serial. The result does not assert that a patch expires after every intervening read or command.

`commit_records_the_executed_effect` checks actual state, possibilities, temporal record, program journal, generation, rights, root and mandate together. ### 9.1 One changing history, with incomplete stages

A write changes relations that determine later reporting and action. Its retained recovery description, the actual configuration reached so far, and access to further commands therefore cannot be treated as independently current facts. The new model first relates them within one unfolding. `Pending` differentiates an origin, prepared target, already changed actual configuration and remaining instruction suffix; `Device.ready` denotes the stage where the current description may again support ordinary use. These are local operational roles, not separately grounded entities. The model omits how storage, enforcement and grants originally form.

Preparation invokes the preceding permission/generation-checked interpreter to construct a target and records the pending description **before any actual field write**. The target is prospective while pending: its candidate list need not contain the intermediate actual configuration. `use` rejects all ordinary reads and commands while pending; changes must enter through `prepare`, and preparation also rejects a competing pending change. The inherited atomic patch is not exposed through `use`.

A tick consumes one additional work unit and time step. If instructions remain, it applies only the next overwrite to the actual configuration. If none remain, it publishes the target description together with the reached actual configuration and removes pending status. The theorem, rather than a comparison with an unseen physical state at runtime, establishes their agreement at that point.

A modeled crash preserves the actual effects, original program, prepared target, pending status and cumulative expenditure. It resets only the remaining instruction list to the whole program and adds the supplied nonnegative delay to the current time. Recovery uses the same tick operation and can itself be interrupted. The pending flag is durable, not a process-local flag cleared by restart.

`exact_result_from_untouched` proves why replay works for this language: states agreeing on the fields untouched by the program have the same fully executed result. Replaying an overwrite prefix cannot affect those untouched fields. This permits repeated same-field assignments, not just pairwise commuting writes. It does not permit arbitrary non-idempotent effects, publication to external parties, uncontrolled faults between writes or changes in the supplied instruction semantics. Such effects need their own recovery relation.

### 9.2 What is preserved and what can finish

`Coherent` says the prepared target remains covered, its actual field equals full execution from the origin, the current actual state agrees on untouched fields, and completing the remaining suffix reaches that target. `funded_suffix_publishes` states an exact sufficient condition. For a coherent pending state with n writes remaining, at least n+1 remaining units and n+1 time steps before the deadline suffice for uninterrupted ticks to publish. Its output has the prepared actual configuration and covered evidence, with exactly n+1 additional units spent and time steps elapsed. Following a crash, n is the **whole program length**, because replay starts over. The theorem does not infer that an interruption-free interval will occur, and finite crashes alone do not imply that sufficient resources remain.

### 10.1 Admission, reservation and stopping

`preflight` computes the prospective prepared state using the existing interpreter and accepts it only when the current grant matches, the existing mandate permits shutdown, and at least three units and three time steps remain. Rejection occurs before an actual field write; this specification assumes an atomic admission/reservation operation. Earlier observations remain paid. It does not assert that real preparation computations are free: the accepted preparation carries the original three-unit charge, and real preflight overhead must be included in a deployment's accounting.

`Armed` joins evidence coherence, grant eligibility and this margin. `Grant` includes an epoch, route, installation serial and signature-validity flag. It is scoped to this prepared episode. Ordinary writes cannot change the protected route or grant, and no concurrent grant revocation is admitted. A prior-generation grant is refused. This does not establish the legitimacy of the grant or acquire it from incomplete evidence.

With remaining reserve R, current time t and deadline D, a pending recovery attempt is allowed only if R ≥ 4 and t + Δ + 4 ≤ D. An uninterrupted attempt uses the inherited single tick, consuming one unit and step. An interrupted attempt retains actual effects, resets replay progress, advances by its delay δ ≤ Δ, and consumes one further work unit and step for the attempted restart. This last work charge is an explicit extension: §9's bare crash still costs only delay. The available margin therefore survives either attempt. The supervisor stops instead when another attempt could consume that margin; it also stops once recovery has published, because this is an episode with an already authorized stopping objective.

`stop` checks the grant and calls the existing `issue → deliver → enact` protocol with a shutdown request. The proof derives completed=true and running=false, exactly three units spent and three steps elapsed, unchanged actual model/fault configuration, retained evidence coherence and consumption of the grant by advancing serial. It does not merely set a supervisor status bit. The physical interpretation of that protocol remains supplied.

`stop_keeps_pending_record` preserves origin, full program, remaining suffix, actual effects, prospective candidates and journal while pending. The pending gate remains closed, and the stopped supervisor is absorbing. Thus stopping does not claim that the unfinished target now describes the intermediate world, roll back the writes, or authorize resuming it later. A later restart would be a separately authorized episode.

### 10.3 Counterreview, prior work and completed scope

**Affirmative argument:** the earlier invariant already carries recovery evidence; a protected reserve connects it to an executable response before that response's enabling conditions are spent. The formal result therefore closes a specific operational inference absent from §9. Preservation of a pending record and finite forced stopping are proved together rather than inferred from a log or a successful example.

**Substantive counterreview (same author):** this construction obtains access by supplying an independently authorized and protected stop channel. It does not prove the original quorum path remains available while pending. If signing that grant requires precisely the unavailable current certificate, entry may be impossible. If shutdown itself can be repeatedly interrupted without a protected completion window, the inherited final protocol theorem does not apply. Arbitrarily long outages, bypass writes, concurrent revocation, resource theft, non-idempotent external effects and physical harm before the deadline are outside the proved guarantee. The model's single Boolean running field is not a physical harm model. Refusing entry may leave an earlier activity running; the claim begins at accepted entry. These are scope limits, not suppressed counterexamples to a stronger claim.

The fallback principle has established precedent. Slagel and colleagues' [2024 NASA runtime-assurance framework](https://ntrs.nasa.gov/citations/20240007986), especially §IV of the [paper](https://ntrs.nasa.gov/api/citations/20240007986/downloads/DASC_submit_slagel_v01.pdf), treats sampled monitoring and the conditions that permit a trusted fallback to preserve a safety property. Our reserve condition is a discrete, resource-accounted connection to the existing recovery model. This is an inference about related structure, not a formal adapter to their PVS development or a claim to invent runtime assurance. Their paper explicitly separates specification verification from industrial deployment difficulties. This source supports the timing/monitor/fallback comparison; it does not validate this grant, Lean code or any hardware.
