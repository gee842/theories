# 器

> 形而上者谓之道,形而下者谓之器。
>                              ——《易·系辞》

---

## 起

《仪》立 wire-level 协议,定 cross-implementation interaction 的 ritual。这份文档接续《仪》,做一件事:把前面一切 commitments 落到具体 stack——展示 间 在不同 language / runtime / library 下如何 instantiate,什么 patterns 跨 stack 共通,什么 patterns 是 stack-specific,什么 pitfalls 容易 violate paradigm。

器不是 specification of "the" implementation——间 没有"the" implementation。器是 reference patterns:几个具体 stack 下如何 build 间,以及为什么这些 stack 自然 fit。任何 implementation 不必精确 follow 这里的 patterns,只需 honor 前面文档的 commitments;但这里的 patterns 是 proven path,在没有 specific 反对理由时是 default 选择。

理事不二,气式构仪器不二。这份文档不是从《仪》派生 implementation,这份文档是同一个 reality 在 concrete instrument register 下的 articulation。

---

## 一、器的姿态

### 多 implementation 而非 the implementation

间 commits to **multiple reference implementations** 而非 single canonical one。理由:

- **范式 not technology**:single canonical implementation 容易让人误以为 间 = that stack。Multiple implementations 让 paradigm 与 technology 分离,paradigm 在 multiple 显现中保持自身。
- **真实的 federation**:仪 promises cross-implementation interop。如果只有一个 implementation,仪 的 cross-impl 维度从未被真正 tested。Multiple implementations interoperating 是仪 的 living validation。
- **不同 strengths**:不同 stack 在不同维度强(BEAM 在 supervision、Pony 在 type safety、Rust 在 performance、Clojure 在 expressiveness)。同一 间 在不同 stack 下显现不同 character——这是丰富,不是不一致。

### Implementation 是 instance,不是 paradigm

任何具体 implementation 是 paradigm 的一个 instance。它有 tradeoffs、有 stack-specific quirks、有 implementation-specific bugs。它不是 paradigm itself。

实践含义:

- 评价一个 implementation 不是问"它是 间 吗"(它当然不是,paradigm 不是 thing)
- 而是问"它 honor 间 commitments 吗"(对照《理》《气》《式》《构》《仪》check)
- 多个 implementation 可以 simultaneously honor commitments,各有 character——这不冲突

### Reference 是 enabling,不是 prescribing

器中的 patterns 不是 mandate。如果 implementer 看清了 specific reasons 走 different path,只要 honor commitments,就是合法 instantiation。

但 reference patterns 是 **proven path**——它们是 implementer 们已经走过、知道 work 的方向。Deviations 需要 careful argument 证明 deviation 不破坏 commitments。Default 跟 reference,deviation 需要 justification——这是 conservative engineering discipline。

## 二、Stack 评估

什么 stack 适合 instantiate 间?评估 dimensions:

### 评估维度

**Actor model 原生支持**:间 is fundamentally actor-based。Stack 越原生 support actor model 越好。BEAM 最强(actor 是 OS-level concept),Pony 强(language built around actors),JVM-based(Akka)中等,Rust+Tokio 中等(actor 通过 library),其他大多数语言弱。

**Lightweight processes**:间 中 actors 数量可能极大(每个 capability、每个 session 都是 actor)。需要 lightweight processes(microseconds spawn,kilobytes memory each)。BEAM 顶级,Pony 强,goroutines 强,thread-based 不可行。

**Supervision 与 fault-tolerance**:Autopoiesis 要求 jian 能 detect 内部 actor 失败、恢复或解体。Native supervision 帮助巨大。BEAM 的 supervision tree 是 reference standard,其他都需要 build。

**Capability discipline**:静态 type system 能在 compile-time enforce capability discipline 是大优势。Pony 的 reference capabilities 顶级,Rust 的 ownership 强,其他需要 runtime check。

**Persistence ecosystem**:Event store 需要 reliable persistence。BEAM 有 Mnesia/ETS,JVM 有充足选择,Rust 有 RocksDB bindings,大部分 stack 都 OK。

**Cryptographic library**:仪 需要 ed25519、blake3、x25519 等。所有 mature stack 都 cover。

**Network ecosystem**:Bridge transport 需要 reliable networking。所有 mature stack 都 OK。

### 候选 stack

**BEAM (Erlang / Elixir)**:Actor model 原生(Erlang processes)、lightweight processes 顶级、supervision tree 标杆、ecosystem 围绕 distributed systems built。Capability 需要 runtime enforcement(无 static type 帮忙)。Performance 比 lower-level 慢但 acceptable。

**Pony**:Reference capabilities 在 type system,actor model 是 core abstraction,zero-cost performance,supervision available。Ecosystem 较小,工程师 base 小,工具 less mature。

**JVM (Akka / Pekko - Scala / Java)**:Akka 提供 actor abstraction,supervision available,巨大 ecosystem,JVM tooling mature。但 actor 是 library 不是 native,有 some impedance,GC 在 large actor systems 有 challenges,capability 全靠 runtime。

**Rust (Tokio + actor crates)**:Performance 顶级,ownership 给 capability discipline 一些静态保证,memory safety,growing ecosystem。但 actor 不是 native,async/await + actor 的 combination 需要 careful design,supervision 需要自建。

**Clojure**:Functional + immutable 适合 event-sourced 设计,REPL 工作流强,JVM 平台资源,core.async 给 some actor-like primitives。但 not natively actor-oriented,需要 build actor abstractions on top。

**Go**:Goroutines 是 lightweight,channel-based concurrency 不是 actor model 但接近。Build actor abstractions feasible。简单部署,大型 ecosystem。但 capability 全 runtime,supervision 需要自建,error handling philosophy 跟 actor model 不太对路。

### 推荐 primary references

考虑以上,推荐三个 primary reference implementations:

1. **BEAM (Erlang)** —— natural fit,supervision tree native,ecosystem aligned
2. **Pony** —— type-level capability discipline,minimum runtime overhead
3. **Rust + Tokio** —— performance-conscious deployments,memory safety,growing community

Secondary references(每个有合理 use case):

- **Clojure** —— REPL-driven development,functional style preference,集成 JVM 资源
- **Akka/Pekko** —— 已有 JVM ecosystem,Java/Scala 团队
- **Go + custom** —— 简单部署需求,small team,operational simplicity 优先

下面 sections 主要 illustrate BEAM-style implementation,with notable contrasts in Pony / Rust / Clojure where they show paradigm-relevant differences。

## 三、L1: Actor 基底实现

### BEAM as primary reference

BEAM(Erlang VM)是 actor model 最 natural 的 implementation 平台,因为 Erlang processes 就是 actors:

```erlang
%% Spawning an actor
ActorRef = spawn(fun () -> actor_loop(InitialState) end).

%% Actor receive loop
actor_loop(State) ->
    receive
        {Message, From} ->
            NewState = handle_message(Message, From, State),
            actor_loop(NewState);
        terminate ->
            ok
    end.

%% Sending a message
ActorRef ! {hello, self()}.
```

BEAM 提供这些 native:

- **Lightweight processes**: process 不是 OS thread,spawn 几微秒,kilobytes 每个,百万级 concurrency feasible
- **Process isolation**: 一个 process crash 不 cascade,只 kill that process
- **Mailbox**: 每 process 自带 mailbox,FIFO,private
- **Supervision**: link / monitor 让 actor 死亡 detectable;`gen_server` + `supervisor` 行为 give structured supervision tree
- **Hot code reload**: actor behavior 可以 update without restart——`become` semantics natively supported

### Pony 对比

Pony 在 actor model 上更进一步:capability discipline 在 type system:

```pony
// Reference capabilities in Pony
class iso MyState  // isolated - exclusive access
class trn MyState  // transitional
class ref MyState  // mutable reference
class val MyState  // immutable
class box MyState  // read-only
class tag MyState  // opaque tag

actor MyActor
  let _state: MyState ref  // actor-private mutable state
  
  be receive_message(msg: String) =>  
    // only this actor can mutate _state
    // no shared mutable state possible
    // ...
```

Pony 让 "actor 之间不 share mutable state" 在 type system enforce——compile-time error if violated。这是 actor discipline 的最强保证。BEAM 通过 process isolation 实现同效果但 runtime 检查。

### Rust + Tokio 对比

Rust 没有 native actor,但 Tokio + custom actor crate 可以 build:

```rust
// Simplified actor using Tokio
struct Actor {
    receiver: mpsc::Receiver<Message>,
    state: ActorState,
}

impl Actor {
    async fn run(mut self) {
        while let Some(msg) = self.receiver.recv().await {
            self.handle(msg).await;
        }
    }
}

// Spawn
let (tx, rx) = mpsc::channel(100);
let actor = Actor { receiver: rx, state: initial };
tokio::spawn(actor.run());
```

Rust 的 ownership 给 actor isolation 一些静态保证(state can't be accidentally shared)。但 supervision 需要 build——没有 BEAM 那样 native supervisor。性能 superior 但 abstraction 重一些。

### 关键 patterns(任何 stack)

不管 stack 选什么,L1 substrate 必须 implement:

```
spawn(behavior, init_state) -> actor_ref
send(target_ref, message) -> ok
receive(within actor) -> message
become(within actor, new_behavior) -> ok
link(target_ref) / monitor(target_ref) -> supervision
```

如果 stack 没有 native support,这些 必须 hand-build。Hand-built version 必须 robust——bug 在 L1 会 cascade 到 L2 以上 everything。

### 不要 reinvent L1

如果 stack 有 mature actor library(Erlang processes、Akka actors、Pony actors),**用它**。不要自己从头 build actor library 除非有 specific reason。L1 不是 间 的 differentiator,L2 才是。L1 用现成的、把 effort 投到 L2 implement 间-specific concerns。

## 四、L2: 间核实现

L2 是 间 specific layer。Patterns 在不同 stack 类似,主要展示 Erlang(参考)+ Clojure(对比)。

### 间(Jian) implementation

BEAM 中 jian 是 `gen_server` 的 specialization:

```erlang
-module(jian).
-behaviour(gen_server).

%% State held by jian
-record(jian_state, {
    inner_actors = #{} :: map(),       %% pid -> actor info
    inner_history = []  :: list(),      %% recent events  
    history_store      :: pid(),        %% event store actor pid
    boundary_behavior  :: fun(),        %% caveat predicate
    visibility_policy  :: fun(),        %% visibility predicate
    autopoiesis_state  :: #autopoiesis{},
    parent_jian        :: pid() | undefined
}).

%% Handle external messages (cross-boundary)
handle_call({external_message, From, To, Msg}, _From_pid, State) ->
    case visibility(From, To, State) of
        true ->
            case caveat(external_msg, From, To, Msg, State) of
                true ->
                    forward_to_inner(To, Msg, State),
                    {reply, ok, record_event(received_external, State)};
                false ->
                    {reply, {error, caveat_denied}, State}
            end;
        false ->
            {reply, {error, not_visible}, State}
    end;

%% Reflexive query: who's in me?
handle_call(members, _From, State) ->
    {reply, maps:keys(State#jian_state.inner_actors), State};

%% Internal actor reports activity (for autopoiesis)
handle_cast({inner_activity, ActorPid}, State) ->
    NewAuto = update_autopoiesis(State#jian_state.autopoiesis_state, ActorPid),
    {noreply, State#jian_state{autopoiesis_state = NewAuto}};

%% Periodic autopoiesis check
handle_info(check_alive, State) ->
    case is_alive(State#jian_state.autopoiesis_state) of
        true -> 
            schedule_next_check(),
            {noreply, State};
        false ->
            initiate_dissolution(State),
            {stop, normal, State}
    end.
```

Key points:

- Jian 是普通 BEAM process(`gen_server`),只是 state 包含额外 fields
- Inner actors 通过 supervisor link 被 tracked——supervisor 自动知道 actor 死亡
- External message 必经 jian process(forced through caveat / visibility checks)
- Autopoiesis 通过 periodic timer + activity tracking 实现

### Clojure 对比

Clojure version using core.async + agents:

```clojure
(defn make-jian [behavior init-state parent]
  (let [inner-actors (atom {})
        history-chan (async/chan 1024)
        in-chan (async/chan 100)
        state (atom init-state)]
    
    ;; Boundary handler loop
    (async/go-loop []
      (when-let [msg (async/<! in-chan)]
        (let [{:keys [from to type content]} msg]
          (cond
            (= type :external-message)
            (when (and (visible? from to @state)
                       (caveat-allows? from to content @state))
              (forward-to-inner to content @inner-actors)
              (async/put! history-chan {:event :received-external
                                         :from from :to to :content content}))
            
            (= type :reflexive-query)
            (handle-reflexive-query msg state inner-actors)))
        (recur)))
    
    ;; Autopoiesis monitor
    (async/go-loop []
      (async/<! (async/timeout autopoiesis-tau))
      (when (alive? @state inner-actors)
        (recur))
      ;; otherwise dissolve
      (initiate-dissolution state inner-actors parent))
    
    ;; Return jian handle
    {:in-chan in-chan
     :inner-actors inner-actors
     :history-chan history-chan}))
```

Differences from Erlang:

- Channels 替代 mailbox(core.async)
- Atoms 给 state mutable container with STM-like semantics
- Go-loops 替代 receive loops
- Less native supervision——必须 manually track child processes

Clojure 的 functional style 让 events 自然是 immutable values,这跟 event sourcing 很 fit。但 actor abstraction 需要 build on core.async,不像 BEAM 那样 native。

### Jian behavior 与 caveat 的 separation

注意 jian 的 `boundary_behavior`(caveat predicate)是 function,**不是 stored config**。这跟《气》的 commitment 一致——caveat 通过当下 evaluation derive,不是 attribute。

Implementation 上:

```erlang
caveat(MsgType, From, To, Msg, State) ->
    %% Function evaluates against current state
    %% Returns boolean
    Behavior = State#jian_state.boundary_behavior,
    Behavior(MsgType, From, To, Msg, State).
```

Behavior function 持有 closure over jian context,evaluation 当下基于 state 做判断。修改 caveat semantics 需要 update behavior function——通过 jian 的 reflexive capability 可以 do this。

### Reflexive capabilities 实现

```erlang
%% Internal admin actor receives reflexive cap
spawn_admin_with_reflexive_cap(JianPid) ->
    Caps = [
        {members, fun () -> gen_server:call(JianPid, members) end},
        {history, fun (Filter) -> gen_server:call(JianPid, {history, Filter}) end},
        {update_caveat, fun (NewBehavior) -> 
            gen_server:cast(JianPid, {update_behavior, NewBehavior}) 
        end},
        {dissolve, fun () -> gen_server:cast(JianPid, dissolve) end}
    ],
    spawn(fun () -> admin_actor_loop(Caps) end).
```

Reflexive capabilities 是 functions(closures),可以 attenuate(wrap with extra check)、可以 delegate(pass to other actors)、可以 revoke(invalidate via terminating closure 的 dependency)。

### Capability(Capability)implementation

Capability 是 forwarder actor。BEAM 中 minimal forwarder:

```erlang
forwarder_loop(Target, Caveats) ->
    receive
        {Msg, From} ->
            case all_caveats_pass(Caveats, Msg, From) of
                true ->
                    Target ! {Msg, self()},  %% forward
                    forwarder_loop(Target, Caveats);
                false ->
                    From ! {error, caveat_denied},
                    forwarder_loop(Target, Caveats)
            end;
        revoke ->
            ok  %% terminate
    end.

%% Create capability
make_capability(Target, Caveats) ->
    spawn(fun () -> forwarder_loop(Target, Caveats) end).

%% Attenuate (create new cap with additional caveat)
attenuate(CapPid, AdditionalCaveat) ->
    spawn(fun () ->
        forwarder_loop(CapPid, [AdditionalCaveat])
    end).
```

每 capability 是独立 process。Attenuation 是 chain of forwarders。Revocation 是 send `revoke` to forwarder。

**Performance concern**:每 capability 一个 process 在 capability-heavy workload 下开销大。BEAM 处理 millions of processes ok,但极端规模下可能想 optimize。Optimization options:

- **Capability 类型 specialization**:常见 capability types(time-bounded、target-specific)用 specific structs + central evaluator,而不是 spawn 完整 actor
- **Capability fusion**:连续 attenuations 可以 fuse into single forwarder with combined caveats
- **Lazy materialization**:capability 只在被使用时 materialize 为 actor

但 optimization 必须保持 paradigm——any optimization that changes capability discipline 是 violation。Default to "every capability is actor",only optimize when measured bottleneck。

### Cryptographic capabilities

仪 中 capability 是 cryptographic certificate chain。Implementation 需要把 wire-form capability 跟 actor-form capability bridge:

```erlang
%% Wire capability arrives
{cap_proof, RootKey, Chain, Subject} = receive_wire_capability(),

%% Verify chain
case verify_capability_chain(RootKey, Chain, Subject) of
    {ok, Authority} ->
        %% Materialize as forwarder actor
        Target = lookup_target(Authority),
        Cap = make_capability(Target, extract_caveats(Chain)),
        Cap;  %% Return actor pid representing this capability
    {error, Reason} ->
        {error, Reason}
end.
```

Wire capability(certificate chain)和 actor capability(forwarder actor)是同一概念在两个 register。Verifier 把 wire form materialize 为 actor,subsequent uses go through actor。Outgoing send 反过来——actor capability serialize 到 wire form。

### Event store implementation

Per-jian event store。BEAM 使用 disk_log 或 RocksDB:

```erlang
-module(jian_event_store).

%% Append event
append_event(StorePid, Event) ->
    gen_server:call(StorePid, {append, Event}).

%% Query by event id
get_event(StorePid, EventId) ->
    gen_server:call(StorePid, {get, EventId}).

%% Query causal past
causal_past(StorePid, EventId) ->
    gen_server:call(StorePid, {causal_past, EventId}).

%% Implementation backed by disk_log
init([JianId, Path]) ->
    {ok, Log} = disk_log:open([
        {name, JianId},
        {file, Path},
        {format, internal}
    ]),
    Index = ets:new(events_idx, [private, set]),
    {ok, #state{log = Log, index = Index}}.

handle_call({append, Event}, _From, State) ->
    EventId = compute_event_id(Event),
    EventWithId = Event#event{id = EventId},
    ok = disk_log:log(State#state.log, EventWithId),
    %% Update index
    ets:insert(State#state.index, {EventId, EventWithId}),
    %% Update prehension index
    update_prehension_index(EventId, Event#event.prehension, State),
    {reply, EventId, State}.
```

Storage backend 是 implementation choice。Common options:

- **disk_log + ETS**(Erlang native)——简单、reliable、reasonable performance
- **RocksDB**——higher performance,跨 stack available
- **PostgreSQL**——relational backing,query flexibility,但 overhead 大
- **Custom log-structured**——maximum performance for specific access patterns

Choice 影响 performance characteristics,但不影响 paradigm。Different jians 可以 different backends——一个 long-history org jian 用 RocksDB,short-lived conversation jian 用 in-memory log。

### Cross-jian event reference materialization

当 event prehends event in another jian:

```erlang
%% Event with cross-jian prehension
ForeignEventRef = #event_ref{
    event_id = ForeignEventId,
    location_hint = ForeignJianRef,
    fetch_capability = FetchCap  %% capability proof
},

%% At creation time, ForeignEventRef stored in this jian's event prehension
%% At query time (if needed):
case fetch_foreign_event(ForeignEventRef) of
    {ok, Event} -> 
        %% Use event content
        Event;
    {error, capability_revoked} ->
        %% Reference still in history but no longer fetchable
        {historical_reference_only, ForeignEventId};
    {error, network} ->
        %% Temporary failure, may retry
        {temporarily_unavailable, ForeignEventId}
end.
```

Lazy fetching——cross-jian event content 只在 needed 时 fetch,不在 prehension 时 eagerly copy。Reduces bandwidth、保持 sovereignty(j_a 不需要 store copy of j_b 的 events)。

### Autopoiesis monitor implementation

Per-jian autopoiesis monitor,通常 in jian process itself:

```erlang
-record(autopoiesis, {
    last_internal_activity :: timestamp(),
    activity_window_seconds :: integer(),    %% τ window
    spawn_count_window :: integer(),         %% recent spawns
    grace_period_remaining :: integer()      %% how many checks before dissolve
}).

is_alive(#autopoiesis{} = Auto) ->
    Now = current_time(),
    Recent = Now - Auto#autopoiesis.activity_window_seconds,
    
    HasRecentActivity = Auto#autopoiesis.last_internal_activity > Recent,
    HasRecentSelfProduction = Auto#autopoiesis.spawn_count_window > 0,
    
    HasRecentActivity orelse HasRecentSelfProduction.

update_on_activity(Auto, ActivityType) ->
    Auto#autopoiesis{
        last_internal_activity = current_time(),
        spawn_count_window = increment_if_spawn(ActivityType, Auto#autopoiesis.spawn_count_window)
    }.

%% Called periodically (timer)
periodic_check(Auto, JianPid) ->
    case is_alive(Auto) of
        true ->
            %% Reset grace period
            Auto#autopoiesis{grace_period_remaining = max_grace};
        false ->
            case Auto#autopoiesis.grace_period_remaining of
                0 ->
                    initiate_dissolution(JianPid),
                    Auto;
                N ->
                    Auto#autopoiesis{grace_period_remaining = N - 1}
            end
    end.
```

Grace period 防止 transient lull 过早 dissolve jian——只有持续 quiescence 才 trigger dissolution。`max_grace` 和 `activity_window_seconds` 是 jian 配置。

### Dissolution flow

```erlang
initiate_dissolution(JianPid) ->
    State = gen_server:call(JianPid, get_state),
    
    %% 1. Emit dissolution event
    DissolveEvent = #event{
        type = jian_dissolved,
        prehension = recent_history(State),
        location = self_ref(State),
        content = #{reason => autopoiesis_failure}
    },
    record_event(DissolveEvent, State),
    
    %% 2. Notify parent
    case State#jian_state.parent_jian of
        undefined -> ok;
        Parent -> Parent ! {child_dissolved, self_ref(State), DissolveEvent}
    end,
    
    %% 3. Release inner actors to parent
    InnerActors = State#jian_state.inner_actors,
    release_to_parent(InnerActors, State#jian_state.parent_jian),
    
    %% 4. Revoke external capabilities
    revoke_external_caps(State),
    
    %% 5. Stop jian process
    ok.
```

Graceful dissolution:everything cleaned up,history preserved through prehension chain,inner actors not killed (just released)。

## 五、L3: 共生层实现

### Bridge implementation

Bridge 是两个 jians 之间的 capability exchange + ongoing message channel。BEAM 中:

```erlang
-module(bridge_actor).

%% State of bridge actor
-record(bridge_state, {
    self_jian :: pid(),                   %% local jian we're part of
    peer_bridge :: pid() | distributed_ref(),  %% peer bridge actor
    peer_capability :: capability(),       %% cap to peer side
    granted_caps :: [capability()],        %% caps we granted to peer
    received_caps :: [capability()],       %% caps peer granted to us
    bridge_id :: bridge_id(),
    health :: bridge_health()
}).

%% Bridge negotiation initiation
init([SelfJian, PeerEndpoint, ProposedTerms]) ->
    %% Send INITIATE message
    InitiateMsg = #{
        type => bridge_negotiate,
        from_jian => self_jian_ref(SelfJian),
        proposed_terms => ProposedTerms,
        attestation => sign(canonical_form(_))
    },
    Result = send_negotiate(PeerEndpoint, InitiateMsg),
    
    case Result of
        {accepted, ResponseMsg} ->
            %% Verify response, extract peer's capabilities
            {ok, establish_bridge(SelfJian, ResponseMsg)};
        {rejected, Reason} ->
            {stop, {bridge_rejected, Reason}}
    end.

%% Forward outgoing message through bridge
handle_call({forward_outgoing, Msg}, _From, State) ->
    %% Repackage with bridge transit attestation
    Repackaged = repackage_with_transit(Msg, State#bridge_state.bridge_id),
    
    %% Send to peer bridge
    send_through_transport(State#bridge_state.peer_bridge, Repackaged),
    
    {reply, ok, update_health_outgoing(State)};

%% Handle incoming from peer bridge
handle_cast({incoming_from_peer, RepackagedMsg}, State) ->
    case verify_transit(RepackagedMsg, State#bridge_state.peer_capability) of
        ok ->
            %% Strip transit wrapper, deliver original
            OriginalMsg = unwrap_transit(RepackagedMsg),
            deliver_to_self_jian(OriginalMsg, State#bridge_state.self_jian),
            {noreply, update_health_incoming(State)};
        {error, Reason} ->
            log_invalid_transit(Reason),
            {noreply, State}
    end;

%% Periodic heartbeat
handle_info(heartbeat_check, State) ->
    case State#bridge_state.health of
        healthy ->
            send_heartbeat(State#bridge_state.peer_bridge),
            schedule_next_heartbeat(),
            {noreply, State};
        timeout ->
            initiate_dissolution(State),
            {stop, normal, State}
    end.
```

Bridge 是 actor pair——两个 jians 各自有 bridge_actor,这两个 actor 通过 transport(distributed Erlang、TCP、libp2p)互相 message。Failure isolation——bridge 失败不直接 kill jian,只是 capabilities revoked。

### Transport choice

Bridge transport 是 implementation choice:

**Distributed Erlang (BEAM-specific)**:Erlang nodes 间 native messaging。Simple、performant、有 Erlang ecosystem 支持。但 only BEAM-to-BEAM。Cross-stack 需要其他。

**gRPC**:Cross-language,mature ecosystem,HTTP/2-based。Schema 需要 explicit(Protobuf)。Suitable for 间 implementations 跨 stacks。

**libp2p**:Peer-to-peer focus,multi-transport,encryption built-in。Complex 但 right shape for federation。Adopted by some distributed protocols。

**Custom over TCP**:Maximum flexibility,需要 implement everything yourself。Only justified if specific needs not met by above。

仪 不强制 specific transport——bridge negotiation 可以协商。但 implementations 通常 default to one and advertise compatibility。

### Identity continuity 实现

跨 jian identity coherence 通过 capability chains。BEAM:

```erlang
%% Root identity actor
-module(root_identity).

init([Pubkey, Privkey]) ->
    {ok, #state{pubkey = Pubkey, privkey = Privkey}}.

%% Issue capability for persona in specific jian
handle_call({issue_persona, JianRef, Caveats}, _From, State) ->
    PersonaCap = #capability_cert{
        issuer = State#state.pubkey,
        subject = generate_persona_pubkey(JianRef),
        authority = persona_in_jian(JianRef),
        caveats = Caveats,
        signature = sign(_, State#state.privkey)
    },
    {reply, {ok, PersonaCap}, State};

%% Respond to identity verification challenge
handle_call({verify_identity_challenge, Challenge}, _From, State) ->
    Response = sign(Challenge, State#state.privkey),
    {reply, {ok, Response}, State}.
```

Persona actor in each jian 是 forwarder to root:

```erlang
persona_actor_loop(RootIdentity, JianRef, PersonaPubkey) ->
    receive
        {challenge, From, Challenge} ->
            %% Forward to root
            {ok, Response} = gen_server:call(RootIdentity, 
                {verify_identity_challenge, Challenge}),
            From ! {challenge_response, Response, PersonaPubkey},
            persona_actor_loop(RootIdentity, JianRef, PersonaPubkey);
        {Message} ->
            %% Application-specific message handling
            persona_actor_loop(RootIdentity, JianRef, PersonaPubkey)
    end.
```

Verification:challenger sends challenge to two personas,both forward to same root,root signs same way,challenger verifies same signature → same identity。No global registry——proof is cryptographic chain。

## 六、跨切关注 (Cross-cutting concerns)

### Persistence

Multiple things need persistence:

- **Event store**: per-jian event history,must survive restart
- **Capability state**: forwarder actors 通常 restartable from cert chains,但 active forwarder state(rate limit counters etc.)需要 persist
- **Jian state**: jian's own behavior + state,通过 standard `gen_server` snapshot 机制

BEAM 的 standard pattern:

- **Mnesia** for structured data with transactions
- **disk_log** for append-only event logs
- **dets** for simple key-value
- **External**: PostgreSQL, RocksDB via NIFs

Strategy:每 jian 自己决定 persistence backend 基于 its character。Long-history org jians use external robust storage,short-lived chat jians use in-memory only(损失 persistence in crash 是 acceptable for those)。

### Observability

Per-jian observability,跟《构》§八 一致。Implementation:

```erlang
%% Health metrics per jian
get_health(JianPid) ->
    State = gen_server:call(JianPid, get_state),
    #{
        autopoiesis => is_alive(State#jian_state.autopoiesis_state),
        member_count => map_size(State#jian_state.inner_actors),
        recent_event_rate => recent_event_rate(State),
        active_bridges => active_bridge_count(State),
        ... 
    }.

%% Tracing through prehension
trace_back(EventId, JianPid) ->
    Event = gen_server:call(JianPid, {get_event, EventId}),
    Predecessors = lists:flatmap(
        fun (PredecessorRef) -> 
            case PredecessorRef#event_ref.location_hint of
                same_jian -> trace_back(PredecessorRef#event_ref.event_id, JianPid);
                {other_jian, OtherJianRef, FetchCap} ->
                    case fetch_foreign(OtherJianRef, FetchCap) of
                        {ok, OtherEvent} -> [OtherEvent | recurse_if_capable(OtherEvent)];
                        _ -> [partially_unreachable(PredecessorRef)]
                    end
            end
        end,
        Event#event.prehension),
    [Event | Predecessors].
```

Tracing 自然 perspectival——trace 通过 capability chain,reachable parts 可见,unreachable parts 标记 unreachable。No god view through tracing。

### Failure handling

Standard BEAM patterns,with 间-specific extensions:

**Actor crash**: supervised by jian's supervisor,restart with last known state(if checkpoint),or fresh state。Capability holders see "actor not alive" error on next message,handle gracefully。

**Jian crash**: parent jian's supervisor catches,records `child_jian_crashed` event,decides restart or release inner actors。

**Bridge break**: bridge actor catches transport error,marks bridge unhealthy,attempts reconnect。If sustained,initiate dissolution。

**Network partition**: bridges marked unhealthy on both sides,each jian continues local autopoiesis,reconnect attempted on recovery。

### Testing

Three layers of testing:

**Unit tests**: per-actor behavior,standard BEAM testing。

**Integration tests**: jian internal dynamics,multi-actor interactions within jian,autopoiesis cycle。

**Conformance tests** against 仪: cross-implementation interop tests。Test suite 在 仪-spec 文档,implementation passes if it correctly handles all defined interactions。

```erlang
%% Conformance test example: bridge negotiation
test_bridge_negotiation() ->
    %% Setup test peer bridge endpoint
    Peer = setup_test_peer(),
    
    %% Initiate negotiation
    Bridge = initiate_bridge(Peer, default_terms()),
    
    %% Verify expected message exchange per 仪 spec
    assert_sent_message(Peer, #{type => bridge_negotiate}),
    
    %% Send accept response from test peer
    send_to_bridge(Bridge, #{type => bridge_response, decision => accept}),
    
    %% Verify confirm message  
    assert_sent_message(Peer, #{type => bridge_confirm}),
    
    %% Verify bridge in active state
    assert_eventually(fun () -> is_active(Bridge) end).
```

Property-based testing(QuickCheck/PropEr)很 fit——JC invariants 是 properties,可以 randomly generate configurations and check invariants hold:

```erlang
prop_no_name_forging() ->
    ?FORALL(Config, gen_jian_config(),
        begin
            FinalConfig = run_random_reductions(Config, 100),
            %% Check: any name in FinalConfig either was in Config 
            %% or generated by explicit (νa) binder
            no_unexplained_names(Config, FinalConfig)
        end).

prop_jian_sovereignty() ->
    ?FORALL({Config, ExternalAction}, {gen_jian_config(), gen_external_action()},
        begin
            Result = apply_external_action(Config, ExternalAction),
            %% Check: jian's inner state only modified if caveat allowed
            modifications_were_caveat_approved(Config, Result, ExternalAction)
        end).
```

### CI / dev workflow

Reasonable workflow:

1. **Local development**: REPL + hot reload(BEAM strong here,Clojure even stronger)
2. **Unit tests**: per-actor logic
3. **Integration tests**: in-process multi-actor scenarios
4. **Property tests**: JC invariants
5. **Conformance tests**: against 仪 spec
6. **Cross-impl interop**: paired with reference implementation in different stack,verify federation

Cross-impl test 是 critical——it's where 仪 promises get validated。

## 七、Common pitfalls

实现 间 时容易踩的坑——这些都 violate paradigm 但 superficially 看像 reasonable engineering。

### Pitfall 1: Stored caveat config

Tempting:

```erlang
%% WRONG
-record(jian_state, {
    caveat_rules = [] :: [rule()]   %% list of rules to check
}).
```

Why 错:caveat 不是 rules,是 derived from current relational state。Stored rules are static config,违反涌现性。

Right:

```erlang
%% RIGHT
-record(jian_state, {
    boundary_behavior :: fun()  %% function evaluated against current state
}).
```

Behavior function 持有 current state context、 capability graph、recent history,evaluation 实时基于这些 derive judgment。

### Pitfall 2: Global registry for cross-jian ID

Tempting:

```erlang
%% WRONG
%% Global ETS table mapping global_id -> actor_pid
maintain_global_actor_registry().
```

Why 错:违反 no god view、no global namespace,以及 substance ontology(actor 有 global ID 暗示 substance identity)。

Right:Capability chain through persona forwarders,verification through cryptographic challenge。No registry needed,identity 是 verifiable claim 不是 stored mapping。

### Pitfall 3: Synchronous cross-jian calls

Tempting:

```erlang
%% WRONG  
result = synchronous_call_to_remote_jian(...)
```

Why 错:Synchronous call across jian boundaries assumes immediate reachability,违反 actor model 的 async 本质。Also cause cascading blocking under partition。

Right:Async messaging,reply via reply_capability,timeout handled gracefully,partition causes capability errors not deadlock。

### Pitfall 4: Centralized event log

Tempting:

```erlang
%% WRONG
%% Single event log for all jians in this deployment
record_event_centrally(Event).
```

Why 错:Centralized log 暗示 god view of all events。Even if "just for this deployment",违反 perspectival semantics。

Right:Per-jian event store。Cross-jian events through prehension references with capability。Aggregate views(if needed)through monitoring jian with appropriate capabilities。

### Pitfall 5: Capability as data not actor

Tempting:

```erlang
%% WRONG
-record(capability, {
    target :: pid(),
    permitted_actions :: [atom()]
}).
%% And then check permitted_actions in target's handler
```

Why 错:Capability 是 data structure,target 自己 check rules。Violates "capability discipline"——capability check is in target,not in capability itself。Easy to bypass。

Right:Capability is forwarder actor,inherently mediates。Target 不需要 know it's been called via capability——它 just receive message,forwarder enforced the discipline。

### Pitfall 6: Stored "current state" as authoritative

Tempting:

```erlang
%% WRONG
-record(jian_state, {
    current_state :: state()  %% The Source of Truth
}).
%% Events 是 just for logging
```

Why 错:违反动静不二——state stored as authoritative,events 降级为 log。Creates state/event divergence possibility。

Right:Events 是 source of truth,state 是 fold of events。State 可以 cache for performance but recomputable from events。Storage architecture 可以 have state snapshots but they're optimization not authority。

### Pitfall 7: Bypassing jian boundary for performance

Tempting:

```erlang
%% WRONG
%% "Trusted" actor in same node bypasses jian boundary check
direct_send_inside_jian(Target, Msg).
```

Why 错:Bypass 一开,paradigm 开始 erode。"Trusted" 不是 ontological category——everyone is in some jian。

Right:Always go through jian boundary。Performance optimization 在 caveat predicate evaluation 内部,不在 bypass。If profiling shows boundary check 是 bottleneck,optimize the check,don't skip it。

### Pitfall 8: Treating jian as namespace not actor

Tempting:

```erlang
%% WRONG  
%% Jian is just a "namespace" identifier
jian_namespace_lookup(JianName, ActorName).
```

Why 错:Jian as namespace 暗示 jian 是 passive structural concept。但 jian 是 actor with reflexive capability、autopoietic dynamics、active boundary judgment。

Right:Jian is process/actor,interactions through messages to jian,jian responds based on its behavior。Treating it as namespace loses everything jian-specific。

## 收

到这里 reference implementation patterns 立住了。

它 honor 了《理》《气》《式》《构》《仪》:

- BEAM as primary reference 因为 actor model native + supervision tree native + 适合 间 ontology
- Multiple stacks 的 reference patterns 展示 paradigm 不绑定 technology
- Common pitfalls section explicit 列出 容易 violate paradigm 的 superficially reasonable engineering choices
- Code sketches 是 patterns,不是 complete implementation——结构而非细节
- Cross-cutting concerns(persistence、observability、testing)在 间 paradigm 下的 specific shape

它 leaves open(deliberately):

- 具体 cryptographic library 选择
- 具体 storage backend
- 具体 transport
- 具体 monitoring infrastructure
- 具体 application-level patterns(应用层是《模式语言》F 的事)

实践 implication:

如果有 BEAM/Erlang 经验,基于 BEAM 起步是最直接路径。`gen_server` 提供 jian-as-actor 的天然形式,supervision tree 处理 fault tolerance,disk_log 处理 event store,distributed Erlang 给 bridge transport 一个 simple-but-functional starting point。

如果优先 type safety,Pony 给 capability discipline 在 type system 的最强保证。Implementation overhead 比 BEAM 略高(ecosystem smaller)but paradigm purity 更强。

如果优先 performance / memory safety,Rust + Tokio + actor crate 是主路径。需要更多 manual work for supervision、interop with cryptographic libraries、event store integration,但 performance ceiling 高。

如果在 JVM ecosystem 已有大量 investment,Akka/Pekko + Java/Scala/Kotlin 是 reasonable。注意 actor abstraction 不像 BEAM 那样 native,GC 在 large actor count 下有 challenges,但 ecosystem maturity 弥补。

如果 functional + REPL 优先,Clojure on JVM 是好选择,虽然 actor abstraction 需要 build on core.async。Event sourcing pattern 在 immutable data 下特别 natural。
