# 仪

> 礼者,天地之序也。
> 序,故群物皆别。
>                              ——《礼记·乐记》

---

## 起

《构》立架构,定 component 间的关系。这份文档接续《构》,做一件事:把跨 implementation、跨 deployment 之间的 wire-level interaction 规范下来,让不同的 间 implementations 能够互相识别、互相通信、互相 federate。

仪不是某个 implementation 的 internal API,不是某个 application 的 protocol,是 **间 与 间 之间 enact 关系的形式**。两个 implementations 即使内部架构有差异,只要 honor 仪,就能 cooperate;不 honor 仪,各自就是孤岛。

仪是间作为 federated reality 的 enabler。没有仪,每个 deployment 是隔离的 sovereignty;有仪,sovereignties 可以建立 structural coupling 而不失去各自 autopoiesis。

仪不规定具体 cryptographic 算法、具体 encoding format、具体 transport——这些是 implementation choice。仪规定 **abstract message structure、必须的 properties、interaction sequences、cryptographic 抽象**。任何实现 follow 仪 的 implementation 跟其他 follow 仪 的 implementation 之间都能 interoperate。

理事不二,气式构仪不二。这份文档不是从《构》派生 protocol,这份文档是同一个 reality 在 wire-level register 下的 articulation。

## 一、仪的姿态

在动笔具体协议之前,先说清几个根本姿态——它们决定每个 protocol decision 的方向。

### 仪 honor 形式

任何 wire-level 设计都必须 traceable 回到《式》的 invariant。如果某个 protocol element 的存在或 behavior 不能 explicit tied to 一条 JC invariant,这个 element 是 questionable。

具体地:

- 一个 "global address namespace" wire format 不能 honor "no god view"——拒绝。
- 一个 "central capability authority" cryptographic structure 不能 honor "no ambient authority"——拒绝。
- 一个 "system-wide event ordering" 协议不能 honor "perspectival semantics"——拒绝。

仪的具体 protocol elements 都是 invariants 在 wire 上的 articulation。

### 仪是 ritual,不是 mechanism

中文"仪"携带一个深的 commitment——仪是 ritual,是 enact relationship 的形式,不只是 mechanism for data transmission。两个 jians 通过 bridge 通信不是"机械传送数据",是 **enact 一段共生关系** 的 ongoing 仪式。

这听起来像形而上的修辞,但有具体 design implication:

- Bridge 的 establishment 是 ceremonial——双方 explicit identification、mutual capability exchange、commitment to ongoing engagement。不是"connect-and-go"。
- Bridge 的 dissolution 也是 ceremonial——dissolution event explicitly recorded、history preserved、capabilities cleanly revoked。不是 silent timeout。
- Cross-jian messages 携带 ritual structure——not just bytes,是 attested、capability-proven、causally-anchored 的 occasion。

这种"ritual character"贯穿仪的每一处。它让协议比纯 mechanism 更 robust,因为 each interaction 在 form 层面已经 enforce 关系性 commitment。

### Implementation-agnostic 但 wire-level committed

仪不 commit:

- 具体 cryptographic 算法(Ed25519 vs BLS,SHA-256 vs BLAKE3)
- 具体 encoding format(CBOR vs Protobuf vs JSON-LD)
- 具体 transport layer(TCP、QUIC、libp2p、WebSocket)
- 具体 fragmentation / batching 策略

仪 commit:

- Abstract message structure
- 必须存在的 fields 和它们的 semantics
- Cryptographic operations 的 abstract structure(signatures over what,verification of what)
- Interaction sequences 的 state machines
- Failure / partition 处理的 expected behavior

不同 implementations 可以选不同 cryptographic suites、encoding formats,只要在 wire 上的 abstract structure 一致。Implementations 在 negotiation phase 协商具体选择(下面 §九 详述)。

### 仪 is conservative

协议是网络效应——一旦 deployed 广泛,改变成本极高。所以仪 in design 极度 conservative:

- 优先 fewer features over more features
- 优先 forward-compatibility over backward-compatibility(让旧 versions 还能跟新 versions 通信)
- 优先 explicit over implicit
- 优先 self-describing over schema-dependent

任何 "nice to have" 不进 core 仪。Core 仪 only contains what's necessary for cross-implementation cooperation 的 minimum。

## 二、Abstract message format

仪的所有 wire-level interaction 都建立在 message envelope 之上。

### Envelope 结构

```
Envelope:
  version: ProtocolVersion        // 协议版本
  source: ActorReference          // 发送方
  target: ActorReference          // 接收方
  msg_id: MessageId               // 唯一 message ID(content-derived)
  causal: CausalContext           // prehension reference
  payload: TypedPayload           // 实际内容
  attestation: Attestation        // 发送方签名
```

### 各 field 的语义

**version**:protocol version。用于 compatibility check(下面 §九)。

**source / target**:两个 ActorReference,具体格式见 §三。注意 source 不是简单的 "sender's name"——它是一个 capability-bearing reference,接收方可以基于此 reference 做 visibility / caveat check。

**msg_id**:唯一标识。Content-derived(比如 hash of envelope 除 attestation 外的 canonical encoding)。这让同一 message 的 retransmission 是 idempotent——接收方看到相同 msg_id 知道是 duplicate。

**causal**:causal context,一组 EventId references(prehension)。表明这个 message 是 prehending 哪些 prior events。这是 prehension 在 wire 上的 articulation——message 不是 isolated event,it carries causal information。

**payload**:typed payload。Self-describing:payload 自带 type tag,接收方不需要 out-of-band schema knowledge。Common types:

- `actor_message`: 普通 actor 间 message
- `capability_op`: capability 相关操作(introduce、attenuate、revoke)
- `event_record`: event 记录
- `bridge_negotiate` / `bridge_active` / `bridge_dissolve`: bridge protocol messages
- `query` / `query_result`: introspection queries
- `system_notice`: lifecycle / autopoiesis notifications

每个 type 有自己的 sub-structure(具体见后续 sections)。

**attestation**:发送方对 envelope canonical encoding 的 cryptographic signature。这给 message 提供:

- **Authenticity**:确保 message 真来自 source claimed
- **Integrity**:envelope content 未被 tampered
- **Non-repudiation**:source 不能事后否认发送

注意 attestation 是 over canonical encoding——specific bytes 在 wire 上可能因 transport 不同而 vary,但 canonical form 是 fixed,signatures verify against canonical form。

### Canonical encoding

任何 implementation 必须能 produce / verify canonical encoding——deterministic byte sequence given the abstract message。这是 attestation verification 的基础。

仪 不规定具体 canonical scheme,但 commit:

- Field ordering 必须 deterministic(usually alphabetical or schema-defined)
- Numbers 必须 canonical representation(no leading zeros、specific endianness)
- Strings 必须 specific Unicode normalization
- Optional fields 处理必须 deterministic(omit vs include with null)

具体 schemes 比如 CBOR canonical encoding (RFC 8949)、JSON canonical form (JCS, RFC 8785)、Protobuf canonical encoding 都 acceptable as long as implementations agree。

### Self-description

Envelope 是 self-describing——版本、payload type、cryptographic 算法选择都 carry in envelope。接收方不需要 prior schema knowledge 就能 parse 基础结构。

具体地,envelope 的 "header" 部分(version、cryptographic suite identifier)总是 in fixed format,即使 envelope 其他部分用不同 encoding。这让 implementations 能 first parse header,then dispatch 到正确 parser。

## 三、Identity 与 references

### ActorReference

Actor 在 wire 上不是简单的 "ID"——它是 capability-bearing reference:

```
ActorReference:
  scheme: "jian"                  // 始终是 "jian://" 开头
  jian_path: List[JianIdentifier] // nested jians from outermost to innermost
  actor_id: ActorIdentifier       // local identifier within innermost jian
  capability: CapabilityProof     // 对此 reference 的 authority
```

具体 wire format 类似:

```
jian://j_outer/j_middle/j_inner/actor_id?cap=<base64-encoded-capability-proof>
```

### Why path-based

`jian_path` 反映 nesting structure——从 outermost reachable jian 到 innermost jian containing the actor。这给 protocol 几个 properties:

- **Routing**:中间 jian 知道如何 forward message(传递给 path 中下一个 jian)
- **Caveat evaluation**:每经过一层 jian boundary,该 jian 可以 evaluate caveat 决定是否 forward
- **Visibility leakage 控制**:发送方需要持有完整 path 上每层 jian 的 capability,otherwise 无法 construct valid reference

注意:**path 不是 absolute namespace**——它是 from sender's perspective 的 reachable path。Different senders 可能有 different paths 到 same actor(through different parent jians、different bridges)。这跟 perspectival semantics 一致。

### JianIdentifier 和 ActorIdentifier

```
JianIdentifier:
  public_key: PublicKey           // jian's identity public key
  short_name: optional String     // human-readable name (informational)

ActorIdentifier:
  local_name: Bytes               // jian-local actor identifier
  // optional: pubkey if actor wants direct identification
  identity_pubkey: optional PublicKey
```

JianIdentifier 总是 includes public key。这让 jian 是 cryptographically identified——不是 by name(can collide),不是 by network address(can change),是 by key(unique and stable)。

ActorIdentifier 中 local_name 是 jian-local——只在该 jian 内部 unique。Same local_name 在不同 jians 中是不同 actors。这是 actor identity is jian-relative 的 wire 表达。

Actor 可以选择性 include identity_pubkey,适用于跨 jian identity verification(见 §四 worldline coherence)。

### Reference is not pointer

Critical 区别:ActorReference **不是** dereferenceable pointer。持有 reference 不意味着可以 message 该 actor——还需要:

- Reference 的 capability proof valid(下面 §四)
- 路径上每层 jian 允许 forwarding(visibility check)
- Target actor still alive

Reference 是 "claim" + "proof",不是 "address"。这跟 ocap discipline 一致——authority comes from capability,reference 是 capability 的 wire form。

## 四、Capability proofs

### CapabilityProof 结构

```
CapabilityProof:
  root: PublicKey                 // 颁发链的根 issuer
  chain: List[CapabilityCert]    // 委托链
```

每个 cert 委托给下一个 subject,形成 chain from root to current holder。

```
CapabilityCert:
  issuer: PublicKey               // 颁发者
  subject: PublicKey              // 接收者(下一个 holder)
  authority: AuthoritySpec        // 此 cert 授予的权限
  caveats: List[Caveat]           // 限制
  expiry: optional Time           // 过期时间
  cert_id: CertId                 // 唯一标识(content hash)
  signature: Signature            // 由 issuer 签名 over above
```

### AuthoritySpec

描述此 capability 授予什么 authority:

```
AuthoritySpec (one of):
  - "send_to": specific actor or jian
  - "enter": specific jian
  - "introspect": specific aspects of jian/actor
  - "attest": authority to attest events
  - "delegate_subset": authority to delegate (subset of held authority)
  - <implementation-defined types>
```

每种 authority 的语义在《式》中已 articulate(visibility、caveat 等);AuthoritySpec 是它们在 wire 上的 representation。

### Caveat

```
Caveat (one of):
  - time_window: {start, end}
  - rate_limit: {max_per_unit_time}
  - target_subset: predicate over messages
  - context_required: specific context required
  - <implementation-defined>
```

Caveats 是 attenuation 在 wire 上的 articulation。Verifier 接到 message 时 check 所有 chain 上的 caveats——每一层 cert 的 caveat 都必须 satisfy,否则 capability 无效。

### Verification

Verifier(收到 reference 的一方)对 CapabilityProof 做:

1. **Root validity**:check 是否 trust this root(local trust decision)
2. **Chain integrity**:每个 cert 的 issuer 是 chain 上一环 cert 的 subject(or root for first cert)
3. **Signatures**:每个 cert 的 signature 由其 issuer's pubkey 验证
4. **Caveats**:每层 cert 的 caveats 在当下 context 下 satisfy
5. **Expiry**:每层 cert unexpired
6. **Authority subset**:每层 delegated authority 是 issuer 持有的 authority 的 subset(no escalation)

任何一条 fail,capability 无效,message rejected。

### Delegation

Holder 持有 cert,可以 delegate(signature 上 with caveats)给新 subject。新 subject 拿到 cert chain (现 chain 加一节),它再可以继续 delegate。

Delegation 不需要联系 root——任何 holder 可以独立 delegate。这是 ocap 的 distributed nature。

但 delegation **不能扩张 authority**——subset only。所以 chain 越长,authority 越窄(每层可能加新 caveats)。

### Revocation

Capability revocation 通过几种 mechanism:

**Expiry**:cert 自带 expiry time,过期自动失效。这是 default revocation 机制。

**Revocation list**:issuer 维护 revoked cert_id list。Verifier 在 high-stakes verifications 中查 revocation status。但 revocation list 是 perspectival——each verifier 维护自己的 list 或 trust 某个 source 的 list,no global revocation registry。

**Forwarder termination**:对应 §六(capability as actor)中 forwarder pattern——capability 的 forwarder actor 被 terminate,subsequent uses fail with "actor not alive"。这是 active revocation,不依赖 revocation list。

实际中三者结合使用——expiry 处理 long-tail、revocation list 处理 stolen credentials、forwarder termination 处理 immediate revocation。

### Sealer / Unsealer

某些 capabilities 需要 confidentiality——只 designated holder 可使用,不能被 inspect 内容。这通过 sealer/unsealer pattern:

```
Sealer<T>: cap that can encrypt T into Sealed<T>
Unsealer<T>: cap that can decrypt Sealed<T> into T
```

通常 sealer 和 unsealer paired——issuer 创建 keypair,sealer 是 encryption capability(distributable widely),unsealer 是 decryption capability(restricted)。这是 ocap 实现 confidentiality 的标准模式。

## 五、Event format

### Event 结构

```
Event:
  id: EventId                     // content-derived hash
  prehension: List[EventReference] // prehended predecessors
  location: JianReference         // 此 event 发生的 jian
  type: EventType                 // event 类型
  content: TypedContent           // event 内容
  timestamp: PhysicalTime         // physical time(informational)
  attestor: PublicKey             // 记录此 event 的 actor's pubkey
  attestation: Signature          // 由 attestor 签名
```

### EventId

```
EventId = hash(canonical_encoding(everything except id and attestation))
```

Content-derived。两个 events 有相同 content + 相同 prehension + 相同 attestation context 会有相同 ID——但因为 prehension 通常引入 uniqueness(referencing different predecessors)和 timestamp,collisions 在 practice 不发生。

EventId 是 content address——任何两方持有同一个 EventId 知道在 referring same event,即使不直接 connected。

### Prehension references

```
EventReference:
  event_id: EventId
  location_hint: optional JianReference  // 哪里能找到这个 event
  fetch_capability: optional CapabilityProof  // 如何 fetch
```

Prehension 不只是 "I prehend event X";它包括 location hint(在哪能找到 X)和 fetch capability(如何 retrieve X 的 content)。

注意 hint 和 capability 都是 optional——如果 X 是 same jian 内 event,hint 不需要;如果 fetch capability 不附带,verifier 必须自己 already have access (或 X 是 公开 event)。

### Event types

Common types:

- `actor_message_received`: actor 收到 message
- `actor_message_sent`: actor 发送 message
- `actor_spawned`: 新 actor created
- `actor_died`: actor terminated
- `jian_spawned`: 新 jian created
- `jian_dissolved`: jian dissolution
- `enter_jian` / `leave_jian`: jian boundary crossing
- `capability_introduced` / `capability_revoked`: capability lifecycle
- `bridge_established` / `bridge_dissolved`: bridge lifecycle
- `<application-defined>`: custom event types

每种 event 的 content schema 由 type 决定。Self-describing——content 携带 type tag,不需要 out-of-band schema。

### Cross-jian event references

当 event in jian j_a prehends event in jian j_b:

```
prehension entry:
  event_id: EventId from j_b
  location_hint: jian://...j_b/...
  fetch_capability: cap to query j_b's event store
```

Fetch capability 是 attenuated——通常只允许 fetch this specific event 或 specific subset,不是 j_b 的所有 events。

如果 fetch capability 后来 revoked,prehension 仍 in j_a 的 history(historical fact)but 不再 traverseable——j_a 知道 "I prehended X" 但不能 retrieve X 的 content。这是 graceful degradation——historical knowledge of relation 比 ongoing access 更 fundamental。

### Event integrity

EventId 是 content hash,所以 event content 的 integrity 通过 hash 验证——任何 mutation 改变 hash,造成 ID mismatch。

Attestor signature provides authenticity——确保 event 真由 claimed attestor 记录。注意 attestor 通常是 "记录 event 的 actor"(for actor messages、it's the receiver / sender);不一定是 some authority。Different attestors 在不同 perspectives 下记录 same factual event——each perspective 是有效的 attestation,no canonical authority。

## 六、Bridge protocol

Bridge 是两个 sovereign jians 建立 structural coupling 的机制。仪 中,bridge protocol 是 explicit ceremonial 流程。

### Phase 1: Discovery

在 negotiation 之前,某个 actor in j_a 必须 know j_b 的 reference。Discovery 机制 outside 仪 scope——可能通过:

- 共同 parent jian 提供 introduction
- 人工 setup(out-of-band exchange)
- Public jian directory (如果存在,但仪 不强制 directory existence)
- Existing bridge 的 transitive introduction

仪 假设 discovery 已发生——actor in j_a 持有 j_b 的 ActorReference (with capability)。

### Phase 2: Negotiation

```
Bridge negotiation sequence:

1. INITIATE
   alice (in j_a) → j_b's bridge endpoint:
   {
     type: bridge_negotiate,
     proposal: {
       initiator_jian: j_a's identifier,
       initiator_capabilities: [caps that alice will grant for this bridge],
       protocol_versions_supported: [v1.0, v1.1, ...],
       cryptographic_suites: [list of supported algorithms],
       proposed_terms: { ... },  // bridge-specific terms
     },
     attestation: alice's signature,
   }

2. RESPOND
   j_b → alice:
   {
     type: bridge_response,
     decision: accept | reject | counter-propose,
     if accept:
       responder_capabilities: [caps that bob's bridge_actor will grant],
       chosen_protocol_version: v1.x,
       chosen_cryptographic_suite: ...,
       agreed_terms: { ... },
     if counter-propose:
       counter_terms: { ... },
     attestation: j_b's signature,
   }

3. CONFIRM (if accepted)
   alice → j_b:
   {
     type: bridge_confirm,
     bridge_id: <derived from negotiation>,
     attestation: alice's signature,
   }

After CONFIRM, both sides have:
- Mutual capabilities to other side's bridge_actor
- Agreed protocol version and crypto suite
- Recorded bridge_established event in their respective histories
```

### Phase 3: Active

After negotiation, bridge is in active phase。Messages flow:

```
alice → j_b actor X:
  envelope:
    target: jian://...j_b/...inner_jians/X
    payload: ...
    
  Routing:
    1. Message sent to bridge_actor in j_a (alice's local capability)
    2. bridge_actor in j_a forwards across bridge to bridge_actor in j_b
    3. bridge_actor in j_b processes through j_b's caveat / visibility checks
    4. If allowed, forwards to actor X within j_b
```

Visibility 和 caveat checks 在每层 jian boundary 进行。所以 message from alice 在 j_a 的 boundary、bridge handover、j_b 的 boundary 各 check 一次。

### Phase 4: Health

Active bridges 需要 health check:

```
Periodic heartbeat:
  bridge_actor_a → bridge_actor_b: { heartbeat, timestamp }
  bridge_actor_b → bridge_actor_a: { heartbeat_ack, timestamp }

If timeouts exceed threshold:
  Bridge is considered unhealthy
  Either side may initiate dissolution
  Or attempt reconciliation
```

Heartbeat frequency 在 negotiation phase 协商。

### Phase 5: Dissolution

```
Either side initiates:
  dissolver → other:
  {
    type: bridge_dissolve,
    reason: voluntary | timeout | policy | other,
    final: true,
    attestation: signature,
  }

Both sides on dissolution:
  1. Revoke capabilities granted to other side's bridge_actor
  2. Record bridge_dissolved event
  3. Notify dependent actors (those with capabilities through this bridge)
  4. Bridge_actor terminates
```

Dissolution 是 graceful——双方都 record event、双方都 cleanup capabilities。If dissolution 是 unilateral(只一方发 dissolve),另一方 timeout 后假设 dissolution。

### Bridge state machine

```
       INITIATE → PROPOSED
                    │
               accept/reject
                    ↓
                 ACCEPTED → CONFIRM → ACTIVE
                    │                   │
                   reject              dissolve
                    ↓                   ↓
                 REJECTED          DISSOLVING → DISSOLVED
```

State transitions are explicit、recorded as events、cryptographically attested。No silent transitions。

## 七、Cross-jian message flow

Message 跨 jian boundary 的具体流程,详细化:

### Sending phase

Alice (in j_a) wants to send to actor X (in j_x, a remote jian connected via bridge):

1. Alice 持有 X's ActorReference: `jian://j_a/.../bridge_actor_a/jian://j_x/.../X`(简化,实际 path 通过 capability 推断)
2. Alice send message to her local representation of X:
   ```
   envelope:
     target: <reference to X with capability proof>
     payload: { ... }
     attestation: alice's signature
   ```
3. Local routing:message 实际 delivered to bridge_actor_a(因为 capability proof 显示 path goes through bridge)

### Bridge transit

Bridge_actor_a 收到 message:

1. Verify alice's capability allows sending through this bridge
2. Repackage message for cross-bridge transit:
   - Original envelope preserved
   - Add bridge transit attestation:
     ```
     bridge_transit:
       from_bridge: bridge_actor_a's identity
       to_bridge: bridge_actor_b's identity
       transit_signature: bridge_actor_a's sig
     ```
3. Send across bridge transport to bridge_actor_b

### Receiving phase

Bridge_actor_b 收到:

1. Verify bridge transit attestation
2. Verify alice's original attestation(alice 的 signature still valid)
3. Verify alice's capability chain ends at credentials valid in j_x's domain
4. Submit to j_x's normal cross-boundary processing(下面 §四 caveat / visibility check)

### Boundary checks at j_x

J_x's boundary behavior:

1. Evaluate visibility:does alice's capability allow reaching X?
2. Evaluate caveat:is this message type / content acceptable per j_x's caveat?
3. If both pass:
   - Record event in j_x's history (received_from_external)
   - Forward to actor X
4. If either fails:
   - Reject with appropriate error
   - Optionally record rejected_external_message event

### Reply path

X 想 reply to alice:

- Alice's reference is in original envelope's source field
- That reference includes alice's capability proof at time of sending
- X 不能 use alice's capability proof to send to alice——X 必须 have its own capability that proves authority to message alice
- 通常 X 的 send-to-alice authority 是 implicit established when alice sent her message(initiating actor 通常给 receiver an implicit reply capability)

Reply protocol detail:

```
When alice sends to X, alice's envelope includes:
  reply_capability: optional CapabilityProof
    - Allows X to send back to alice
    - Typically with caveats limiting to "in this conversation"
    - Often time-bounded
```

X 收到 message,持有 reply_capability,可以 send back through it。如果 alice 没 include reply_capability,X 默认无 authority to message alice (除非 X 通过 other channels 已持有 such capability)。

### Error 流

任何阶段 fail,error 通过 same path 反向:

- Bridge transit fail (network):alice's bridge_actor 接到 timeout / network error
- Alice's capability invalid:bridge_actor_b reject,error returned through bridge
- Visibility / caveat denied:j_x's boundary reject,error returned

Errors 是 first-class events——recorded in sender's history、includes attestation by rejecting party、carries reason code。这让 distributed debugging 可以 trace error 的 origin。

## 八、Partition & reconciliation

Distributed system 不可避免遇到 partition——网络断了、bridge 失去 connectivity、双方各自 continue 但分别 evolve。

### Partition detection

通过 heartbeat timeout 检测。但 timeout 不一定 means "permanent partition"——可能是 transient network blip。

Strategies:

- **Conservative**:long timeouts before declaring partition,risk slow detection but fewer false positives
- **Aggressive**:short timeouts,quick detection but more false positives
- **Adaptive**:base on observed network patterns

仪不 prescribe specific strategy——bridge negotiation 可以协商。

### During partition

Each side:

1. Mark bridge as "partitioned"
2. Continue local autopoiesis(internal activity 不依赖 bridge)
3. Queue messages for partitioned bridge(or apply application-level fallback)
4. Optionally attempt reconnection

### Reconnection

When connectivity restored:

1. Bridges 互相 detect via heartbeat resumption
2. Re-attestation:双方 verify each other's identity didn't change
3. State synchronization:bridge specific—下面 details

### State synchronization

After reconnection,双方 state 可能 diverged(各自有 events the other doesn't know about during partition)。Sync strategies:

**Event log sync**:exchange events generated during partition,prehension graph 自动 reconciles ordering。但 only valid for events that both sides can reasonably expect to share。

**Last-known-event marker**:每一方 track "I know peer's history up to event_id X"。On reconnect,exchange new events since X。

**No sync (intentional)**:某些 application 决定 partition 期间各自演化是 acceptable,不试图 reconcile。Bridge 重新 establish 但 history streams 各自独立。

**Application-level reconcile**:仪 不规定 application-level reconciliation——各 jian 自己决定 conflicts 怎么处理(CRDT、operational transform、manual merge、abort)。

### Permanent partition

If reconnection 长时间不成,bridge is considered permanently dissolved:

- Each side proceeds with bridge_dissolved
- Capabilities revoked
- Records partition_dissolution event distinguishing from voluntary dissolve

Actors in either jian that depended on cross-jian capability discover capability invalid,handle gracefully (retry、fallback、user notification)。

## 九、Versioning 与 evolution

### Version 标识

```
ProtocolVersion:
  major: integer
  minor: integer
  patch: integer
  cryptographic_suite: SuiteIdentifier
  extensions: List[ExtensionId]      // optional features
```

Major 变化 = breaking changes。Minor = additive。Patch = bug fixes。

Cryptographic suite 是 separately identified——同 protocol version 可以用不同 suites(比如 v1.0 with Ed25519 vs v1.0 with BLS)。这让 cryptographic agility 可能。

### Negotiation 流程

Bridge negotiation phase 包含 version negotiation:

```
Initiator advertises:
  versions_supported: [v1.0, v1.1, v2.0]
  suites_supported: [Ed25519+SHA256, BLS+BLAKE3]
  extensions: [ext_a, ext_b]

Responder selects:
  chosen_version: v1.1
  chosen_suite: Ed25519+SHA256
  chosen_extensions: [ext_a]  // intersection of mutual support
```

If no mutual support——bridge fails to establish with clear error。

### Forward compatibility

Newer versions 必须能 talk to older versions(in older version's protocol)。这是 conservative design:

- New features 通过 extensions 添加,not core changes
- Old fields 不被 removed (deprecated 但 maintained)
- Unknown fields 被 ignore (not error)
- Self-describing payload types means old parsers can skip new types

### Backward compatibility

Older versions 不必能 understand newer features——但必须 gracefully refuse,not silently misbehave。Newer side 检测 older side,降到 mutual lowest version。

### Major version transition

When major version change is needed (some breaking change),strategy:

1. Announce 新 major version with timeline
2. Implementations 同时 support 新旧 versions for transition period
3. Bridges negotiate to highest mutual,落到旧 version if mutual not 新
4. Eventually old version deprecated and removed

仪 commit to **long deprecation cycles**——changes affect 网络 state,不能急。

### Extension mechanism

Extensions 是 opt-in features:

```
Extension example:
  id: "ext.zkp_capability"  // namespaced
  description: "Zero-knowledge capability proofs"
  fields_added: { ... }
  semantics: { ... }
```

Implementations advertise supported extensions in negotiation,bridge uses intersection。Unknown extensions 不 break basic communication——they just enable additional features when both sides support。

This lets 仪 evolve without breaking core——experimental features in extensions,proven ones eventually merged into core minor versions。

## 十、Concrete encoding examples

仪 是 abstract——任何 encoding satisfying 仪 的 abstract structure works。下面 sketch 几个 concrete encodings,展示 same envelope 的不同 wire form。

### CBOR encoding (recommended for performance)

```
Envelope (CBOR):
  - Map with integer keys (efficient):
    1: version (text)
    2: source (CBOR-encoded ActorReference)
    3: target (CBOR-encoded ActorReference)
    4: msg_id (byte string)
    5: causal (CBOR array of EventReferences)
    6: payload (CBOR-encoded TypedPayload)
    7: attestation (byte string - signature bytes)
```

CBOR canonical encoding (deterministic) for signature。Compact、fast、widely supported(rfc 8949)。

### JSON encoding (recommended for debugging / interop)

```json
{
  "version": "1.0",
  "source": {
    "scheme": "jian",
    "jian_path": ["pubkey:abc...", "pubkey:def..."],
    "actor_id": "alice",
    "capability": { ... }
  },
  "target": { ... },
  "msg_id": "base64:...",
  "causal": [
    { "event_id": "blake3:...", "location_hint": "jian://...", "fetch_cap": "..." }
  ],
  "payload": {
    "type": "actor_message",
    "content": { ... }
  },
  "attestation": "base64:..."
}
```

JCS (RFC 8785) for canonical encoding。Verbose but human-readable—good for development、debugging、cross-implementation testing。

### Protocol Buffers encoding (recommended for tightly-coupled systems)

```protobuf
message Envelope {
  string version = 1;
  ActorReference source = 2;
  ActorReference target = 3;
  bytes msg_id = 4;
  repeated EventReference causal = 5;
  TypedPayload payload = 6;
  bytes attestation = 7;
}

message ActorReference {
  string scheme = 1;
  repeated string jian_path = 2;
  string actor_id = 3;
  CapabilityProof capability = 4;
}

// ... etc
```

Strongly typed、efficient、good tooling。Trade-off:less self-describing,需要 schema sharing。

### Choosing encoding

Implementations 通常 default to one(CBOR for performance, JSON for debugging),advertise others as alternatives in negotiation。Bridge 选 mutual best。

Encoding choice 不影响 abstract structure——所有 encodings encode same envelope semantics。Implementations 可以 multi-encode(用不同 encodings 跟不同 peers 通信)。

### Cryptographic suite specification

每个 suite includes:

```
Suite specification:
  signature_algorithm: e.g. "Ed25519"
  hash_algorithm: e.g. "BLAKE3-256"
  symmetric_encryption: e.g. "ChaCha20-Poly1305"
  key_exchange: e.g. "X25519"
  canonical_encoding: e.g. "CBOR-canonical"
```

Recommended default suite (v1.0):

- Ed25519 for signatures
- BLAKE3-256 for hashes
- X25519 for key exchange
- ChaCha20-Poly1305 for symmetric encryption
- CBOR canonical for attestation encoding

This is recommendation,not mandate—implementations 可以 negotiate other suites if both support。

## 收

到这里 wire-level protocol 的 core 立住了。

它 honor 了《理》《气》《式》《构》:

- 所有 wire-level structures honor JC invariants —— no global namespace, capability discipline 通过 cryptographic chains, prehension on the wire as causal references
- 所有 protocol elements 是 ritual 不是 mechanism —— bridge negotiation 是 ceremonial, dissolution 是 graceful, error 是 first-class events
- Implementation-agnostic —— specific algorithms / encodings / transports are choices, abstract structure is committed
- Cross-implementation interoperability —— different implementations of 间 internally 可以 architecturally vary,只要 follow 仪 就能互 federate

它 leaves open(deliberately):

- 具体 cryptographic 算法选择(suite agility)
- 具体 encoding format(CBOR / JSON / Protobuf 等)
- 具体 transport(TCP / QUIC / libp2p)
- 具体 reconciliation strategies(application choice)
- 具体 bridge discovery mechanisms

这些是 implementation 或 deployment choices,不是 protocol commitments。

后续文档:

**实现(D)**:reference implementations。具体 language / runtime / library 的 sample implementation,展示 仪 在实际工程中的 instantiation。可能 multiple references——展示同一仪可以 multiple incarnations。

**模式语言(F)**:常见 protocol patterns——specific bridge topologies、specific capability patterns(membrane、sealer、saga)、specific reconciliation strategies。这是 working with 仪 的 vocabulary。

**生态(G)**:运营层 concerns——federation governance、capability hygiene、long-running protocol evolution、cross-deployment migration。

但 again,这些是后续。这份《仪》立 wire-level skeleton——任何两个 implementations 通过它能 cooperate;任何 implementation 想要参与 间 ecosystem 必须 follow 仪。

理立则气有方,气行则式有据,式定则构有形,构成则仪有节,仪行则器有度。
