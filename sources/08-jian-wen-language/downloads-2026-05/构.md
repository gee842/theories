# 构

> 备物致用,立成器以为天下利,莫大乎圣人。

---

## 起

《理》立根基,《气》言对应,《式》立形式系统。这份文档接续《式》,做一件事:把 JC 的 reduction system 翻译成具体的 component organization——什么模块、各自的责任、模块之间如何 compose,使得任何 implementation 走这个 architecture 就 naturally honor JC 的 invariants。

构不是 specification,不是 implementation guide,不是 deployment blueprint。构是 **the shape that any 间 implementation must take to honor 间**——它 commits 到 components 和 their relationships,但 leaves open 具体语言、具体 runtime、具体存储、具体网络协议。

构的目的:让工程师在做具体决策时,有 reference 可以回去检查"这个决策是否 honoring 整体 architecture"。当某个 implementation 想要 deviate from 这个 architecture,它必须明确知道自己在 deviate 什么,以及 deviation 的 cost 是什么。

理事不二,气式构不二。这份文档不是从《式》派生 architecture,这份文档是同一个 reality 在 component register 下的 articulation。

---

## 一、构的姿态

在动笔架构之前,先说清几个根本姿态——这些姿态决定每一个 architectural decision 的方向。

### 架构 honor 形式

任何 component 设计都必须 traceable 回到《式》的 invariant。如果某个 component 的存在或 behavior 不能 explicitly tied to 一条 JC invariant 或 reduction rule,这个 component 的 design 是 questionable。

具体地:

- 一个 "global registry" component 不能 honor "no god view"——直接拒绝。
- 一个 "central scheduler" component 不能 honor "local reduction"——直接拒绝。
- 一个 "permission ACL service" component 不能 honor "derived predicates not stored"——直接拒绝。

这听起来像约束,实际上是 simplification——它直接砍掉了大类 architectural temptations,让设计空间更清晰。

### Implementation-agnostic but structurally committed

构不 commit:

- 具体语言(Erlang、Clojure、Rust、Pony、其他)
- 具体 runtime(BEAM、JVM、native、wasm)
- 具体存储(SQL、KV、graph、log-structured)
- 具体网络协议(gRPC、自定义、QUIC、libp2p)
- 具体调度策略(work-stealing、actor-per-thread、cooperative)

构 commit:

- Component 的 responsibilities
- Component 之间的 dependencies 方向
- Component 间的 interaction patterns
- Per-component invariants

任何 implementation 可以选择不同的具体技术,但必须保持 component 结构。换技术不动结构,是 implementation choice;改结构,就是 deviating from 间的 architectural commitment。

### 架构是 enabling 不是 prescribing

构不规定 "你必须这样做",构 articulate "这样做能 naturally honor 间"。如果有人发明了 differently 的架构 also honors JC invariants,那个架构也是合法的——构不是 唯一路径。

但 in practice,JC 的 invariants 强烈 suggest 我们这里描述的 component 结构。Deviations 通常是可能的,但需要 careful argument 证明 deviation 不破坏 invariants。

## 二、整体层次

间的 architecture 有自然的 5 层结构:

```
┌─────────────────────────────────────────┐
│ L4: 应用层                                │
│      Applications, agents, user systems  │
├─────────────────────────────────────────┤
│ L3: 共生层                                │
│      Bridges, federation, identity       │
├─────────────────────────────────────────┤
│ L2: 间核                                  │
│      Jian, capability, events, alive    │
├─────────────────────────────────────────┤
│ L1: actor 基底                            │
│      Actor runtime, mailboxes, scheduler│
├─────────────────────────────────────────┤
│ L0: 介质层                                │
│      Network, storage, OS processes      │
└─────────────────────────────────────────┘
```

### 各层的责任

**L0 介质层**:OS、网络、存储等 underlying 资源。间不直接操作这一层,但所有上层最终落到这一层。L0 不是间的 part,是间运行其上的 substrate。

**L1 actor 基底**:实现 actor model 的核心 primitives——mailbox、scheduler、spawn / send / become。这一层 honors actor model 但不知道 jian、capability、events 这些 间-specific 概念。理论上 L1 可以是任何 mature actor runtime(BEAM、Akka、自实现)。

**L2 间核**:间 specific 的 components——jian 作为 nested actor,capability 作为 forwarder,event store with prehension,autopoiesis monitor。这一层 implement JC 的 reduction relation 和 invariants。

**L3 共生层**:跨 jian 的 cooperation 机制——bridges、federation、cross-jian identity。这一层 honor structural coupling commitment。

**L4 应用层**:具体的 application logic——具体 agent 系统、具体 community network、具体业务流程。这一层用 L3 以下提供的 primitives 构建。

### 层与层之间的纪律

**Up-only dependency**:L_i 只 depend on L_j where j < i。下层不 depend on 上层。

**No layer skipping for jian-relevant concerns**:L4 应用如果要关心 jian 边界、capability、events,必须通过 L2 接口。绕过 L2 直接访问 L1 actor 是允许的(普通 actor model usage)但意味着 L4 应用不再 in 间 ontology——它 just 用 actor model。

**Each layer 自包含**:每层暴露给上层的接口必须 fully self-describing。上层不需要"穿透" lower layer 才能正确使用——这是 abstraction discipline。

### 不存在的层

注意几个 conventional architectural layers 在间中**不存在**:

- **No global state layer**:没有"the system state",只有 distributed state across actors / jians。
- **No central control layer**:没有 master node、orchestration manager、universal scheduler。
- **No central registry layer**:没有 service registry、name registry、capability registry。
- **No global monitoring layer**:观察是 perspectival 的,任何 monitoring 是 jian itself。

这些不是 omission——是 deliberate exclusions, deriving from 式 的 invariants。

## 三、L0-L1:介质与 actor 基底

### L0:介质层

间运行在某种 underlying medium 上——OS、虚拟机、容器、wasm runtime、bare metal。介质层提供:

- **进程隔离**:actor runtime 自己的 process / sandbox
- **网络通信**:跨进程、跨机器的 message passing
- **持久存储**:event 持久化、state 持久化
- **时钟**:逻辑时间(causal)与物理时间(autopoiesis 的 τ window)

间不 directly 处理这些——它们是 L1 actor runtime 的 implementation concerns。但间 commit 到 L0 必须能 support 几个 minimum properties:

- **Failure isolation**:一个 actor 崩溃不应当 cascade 到整个 process。
- **At-least-once delivery 或更强**:message 传递必须 reliable enough,otherwise causal reasoning 失败。
- **Persistent storage**:events 必须能持久化,otherwise history fold 不可能。

如果 L0 不能 provide 这些(比如某些极端嵌入式环境),间在那个环境上不 deployable——这不是 architecture failure,是 environment 的 fundamental limitation。

### L1:actor 基底

L1 提供 actor model 的 core runtime。接口大致如下:

```
Actor runtime API (conceptual):
  spawn(behavior, init_state) → ActorRef
  send(target_ref, message) → ()
  receive() → message       (within actor)
  become(new_behavior) → ()  (within actor)
  link(target_ref) → ()      (supervision)
  monitor(target_ref) → ()
```

具体 implementation 可以是:

- **BEAM (Erlang/Elixir)**:成熟、battle-tested、有 supervision、有 hot code reload。最自然的 reference。
- **Pony**:reference capabilities + actor,在类型层 enforce 一些 capability discipline。形式上更 strong。
- **Akka / Pekko (JVM)**:成熟但 supervision model 不如 BEAM 干净,actor message 通常需要 type 化。
- **Tokio + 自定义 actor 抽象 (Rust)**:performance 强,但 actor model 不是 Rust native,需要 careful design。
- **自实现**:如果 above 都不合适。需要自己处理 mailbox、scheduling、supervision。

### L1 component 责任

**Mailbox manager**:per-actor mailbox。FIFO 或 priority,implementation choice。Mailbox 是 actor 私有的——其他 actor 通过 send 进入 mailbox,但不能 directly read/modify 它。

**Scheduler**:决定哪个 actor 何时 run。Strategies:

- **Cooperative**:actor 自愿 yield。简单但容易卡住整个 system。
- **Preemptive**:runtime 强制 yield。更 robust 但需要 instrumentation。
- **Work-stealing**:多个 worker 共享 actor pool。BEAM 用这个。

间不 commit 到 specific strategy,但 commit 到 fairness——长期看,任何 active actor 必须得到 scheduling。否则 jian autopoiesis 的"recent activity"判断会被 starve。

**Spawn manager**:create 新 actors,assign fresh names,initial behavior + state setup。Names 必须 fresh(no name forging invariant 要求)。

**Supervision**:actor 死亡 / 异常时,linked / monitoring actors 收到 notification。这给 jian 一个 natural mechanism 检测内部 actor 失败。

### L1 不知道的

L1 deliberately 不知道:

- **Jian** 是什么——L1 只看到 actors,不知道哪些 actors 是 jian。
- **Capability** 的语义——L1 只看到 actor references,不知道 reference 的 capability character。
- **Events** 的 prehension——L1 messages 是 transient bytes,event store 在 L2。
- **Autopoiesis** 监控——L1 只 track actor 生死,jian liveness 在 L2。

这是 layered abstraction 的 discipline——L1 关心 actor model 的 universals,间-specific concerns 在 L2。这让 L1 可以 swap implementation 而不影响 L2 以上的逻辑。

## 四、L2:间核

L2 是间的 specific layer,implement 式中的 jian-specific concepts。它有四个 sub-components:

```
┌────────────────────────────────────────────┐
│              L2: 间核                       │
│                                            │
│  ┌──────────┐   ┌──────────┐              │
│  │  Jian    │   │Capability│              │
│  │ Manager  │←──│  Layer   │              │
│  └──────────┘   └──────────┘              │
│        ↓             ↓                     │
│  ┌──────────┐   ┌──────────┐              │
│  │  Event   │   │Autopoiesis│             │
│  │  Store   │   │  Monitor │              │
│  └──────────┘   └──────────┘              │
│                                            │
└────────────────────────────────────────────┘
```

四个 sub-components 互相依赖但责任分离。

### 间 (Jian Manager)

每个 jian 在 implementation 中是一个 actor(L1 上的普通 actor)加上 jian-specific 扩展:

```
JianActor structure (conceptual):
  - actor_ref: L1 actor reference
  - inner_actors: managed set of nested actors
  - inner_history: event store for jian's internal events
  - boundary_behavior: caveat predicate logic (B_j)
  - reflexive_caps: introspection / modification capabilities
  - liveness_state: autopoiesis tracking
```

**Jian 的 behavior** `B_j` 处理:

- 接收 enter/leave 请求,evaluate caveat,allow/deny
- 接收 cross-boundary message,evaluate visibility,forward/deny
- 接收 reflexive query,response with introspection result
- Spawn 内部 actors,track 它们 in `inner_actors`
- Emit events to inner_history
- Periodically check liveness condition

**Inner_actors 不是 stored attribute**——它是 ongoing tracked structure。Jian 通过 supervision link 知道哪些 actors 是 alive in 自己内部。Actor 死亡,jian 收到 notification,update inner_actors。这跟"membership 是 derived from autopoietic activity"一致。

**Reflexive capabilities**:jian 暴露给自己的 introspection / modification API:

```
reflexive caps (conceptual):
  members() → query inner_actors
  history(filter) → query inner_history
  spawn_inner(behavior) → spawn actor inside self
  emit(event_content, prehension) → record event
  check_liveness() → autopoiesis status
  initiate_dissolution() → voluntary dissolve
```

这些是 first-class capabilities,可以被 attenuated and passed to selected internal actors。比如 admin actor 可以拿到 full reflexive caps,普通 member 只拿到 attenuated members() 和 history(self) capabilities。

**Cross-boundary 处理**:外部 actor message 内部 actor 时,流程:

1. Message 实际 send 到 jian 自己的 mailbox(因为外部只看到 jian 的 reference)
2. Jian behavior 解析 target 是内部 actor
3. Jian evaluate visibility(基于 sender's capability)
4. 允许则 forward 给内部 actor;否则 reject

这意味着 jian 是 cross-boundary message 的 mediator。Performance 上看起来 expensive,但 honor "no direct external access" 的 commitment——不能 bypass jian 直接 message 内部 actor。

### Capability Layer

Capability 本身是 forwarder actor(L1 上的普通 actor),其 behavior 是 forward + attenuate + revoke。

**Capability creation patterns**:

```
Direct capability (no attenuation):
  forwarder: receive(m, v) → send(target, m, v)

Attenuated capability:
  forwarder: receive(m, v) → 
    if predicate(m, v):
      send(target, m, v)
    else:
      reject

Time-bounded capability:
  forwarder: receive(m, v) →
    if current_time < expiry:
      send(target, m, v)
    else:
      auto_terminate()  // capability dies, future messages fail

Membrane (multi-capability wrapper):
  forwarder: receive(m, v) →
    audit(m, v)
    transform(m, v) to (m', v')
    send(target, m', v')
```

**Capability discipline 的 enforcement**:

- 只能通过 introduction 获得 capability(spawn 时被 init,或通过 message receive)
- L1 不允许 reference forging(actor 不能凭空 fabricate references)
- Capability 的 attenuation 通过 forwarder behavior 实现,不通过 special primitive
- Revocation 通过 terminating forwarder 实现

**Capability graph 是 implicit**:

间 architecture 中**没有 central capability registry**。Capability graph 是 emerge from actor reference holdings——每个 actor 知道自己持有哪些 references,但没有谁知道"the global capability graph"。

这意味着 visibility predicate 的 evaluation 需要小心——它不能 query "the graph",它必须 traverse capability chain through actual message passing。在 practice,这意味着 visibility 检查通常 reactive(尝试 forward,失败则 reject)而不是 prescient。

### Event Store

Per-jian event store:每个 jian 有自己的 event storage。跨 jian event reference 通过 capability。

**Event 结构**:

```
StoredEvent:
  id: EventId
  prehension: Set<EventId>
  content: bytes (or structured payload)
  location: JianRef
  timestamp: physical time (informational, not authoritative)
```

**Storage 策略**:

- **Append-only log per jian**:简单、快、causally ordered。BEAM 的 persistent_term + DETS 或 RocksDB 都行。
- **Indexed by EventId**:fast lookup,通常 hash table。
- **Indexed by prehension**:fast causal query。可选,memory cost。

不同 jian 可以选不同 storage——长 history 的组织 jian 可能用 disk-backed log,短暂 conversation jian 可能纯 memory。

**Query patterns**:

- `get(event_id)` → `Event`
- `prehended_by(event_id)` → `Set<EventId>`(它的直接前驱)
- `prehends(event_id)` → `Set<EventId>`(prehending 它的后继)
- `causal_past(event_id)` → `Set<EventId>`(整个 prehension closure)
- `range(start_time, end_time)` → events in physical time window
- `filter(predicate)` → events matching some content predicate

**Cross-jian event reference**:

如果 event in jian j_a prehends event in jian j_b,需要:

1. j_a 的 actor 持有 capability 到 j_b's event store
2. 通过 capability query j_b's event,获得 reference
3. j_a 的新 event 在 prehension 中包含 cross-jian reference

Cross-jian reference 是 capability,不是 absolute pointer。如果 capability 被 revoked,reference 仍然存在但不再 traverseable——event 在 j_a 中仍知道"我曾 prehend j_b 的某个 event"作为 historical fact,but 不再能 query 该 event。

**Event GC**:

Events 不会无限堆积。GC 策略:

- 不被任何 active actor / future event reference 的 events 可以 archive(冷存储)
- Archived events 仍存在但 query 慢
- 长期不被 reference 的 archived events 最终可被 forget(implementation choice;某些 jian 可能选择 永远保留)

GC 是 per-jian decision,不是 system-wide。

### Autopoiesis Monitor

每个 jian 有自己的 autopoiesis monitor——不是一个 separate global service,是 jian 自身 behavior 的一部分。

**Monitoring cycle**:

```
periodic (with frequency related to τ):
  check internal activity in last τ
  check self-production (spawns / state changes in last τ)
  check boundary maintenance (caveat / visibility evaluable)
  if any check failed for sustained period:
    initiate dissolution
```

**τ 的选择**:

- **长寿命 jian**(组织、社区、长期项目):τ 较长(小时、天、周)。某段时间没活动是正常的。
- **短寿命 jian**(会话、临时合作、单次任务):τ 较短(秒、分钟)。停止活动应当 quickly dissolve。
- **极短寿命 jian**(short-lived sessions, ad-hoc coordination):τ 极短(毫秒、秒)。

τ 是每个 jian 自己的 configuration,可以 explicit set 或基于 jian 的 type / role 推断。

**Dissolution 流程**:

```
dissolve(jian):
  1. emit dissolution event (with prehension to recent history)
  2. notify parent jian (if any)
  3. release internal actors:
     - move them to parent jian's inner_actors, OR
     - return them to their pre-jian location
  4. revoke capabilities held by external actors to internal actors
  5. archive history (parent jian inherits prehension links)
  6. terminate jian's own actor
```

**Cascading**:

如果一个 jian 包含 child jians,parent dissolve 时 children 也 dissolve(通过 supervision)。Children 的 history 成为 parent 的 history(通过 prehension chain)。

注意:cascade 不是 forced——child jian 可以 negotiate "我想 outlive parent",通过 explicit bridge 到 grandparent。这是 design decision per jian,不是 default behavior。

## 五、L3:共生层

L2 处理单 jian 内部 dynamics。L3 处理 jian 之间的 cooperation。

### Bridges(结构耦合)

Bridge 是两个 sovereign jians 之间的 capability exchange。implementation 上,bridge 是:

```
Bridge structure:
  jian_a's bridge_actor: holds capability to jian_b's bridge_actor
  jian_b's bridge_actor: holds capability to jian_a's bridge_actor
  
  Two bridge_actors form a bidirectional channel.
```

**Bridge lifecycle**:

1. **Negotiation**:某个 actor in j_a 想 connect to j_b。它通过外部 introduction(可能通过共同 parent jian、可能通过人工 setup)获得 j_b 的 reference。
2. **Capability exchange**:j_a 创建 bridge_actor,持有"代表 j_a 跟 j_b 通信"的 capability。j_b 同样。两个 bridge_actor 互相持有 capability。
3. **Active phase**:bridge_actors 互相 forward messages between 两 jian 的 inner actors(through 各自 jian 的 boundary checks)。
4. **Decoupling**:任一方 revoke capability,bridge 终止。Other side 收到 capability error。

**No shared state**:

Bridge 不维护 shared state。Bridge 只 forward messages。任何"shared knowledge"必须通过 explicit replication(messages exchanging state copies)实现,with 两边各自决定如何 reconcile。

**Bridge 失败处理**:

- 网络 partition:bridge messages 无法送达,bridge_actor 收到 timeout / error。各 jian 继续 autopoietic existence。
- Reconnection:重新 negotiate capabilities(可能是 same actors with refreshed capabilities,or new bridge instance)。Reconnection 后 state 可能 diverged——需要 application-level reconciliation。

### Federation

Federation = 多个 sovereign jians + 它们之间的 bridge network:

```
       ┌──────┐ ←─────→ ┌──────┐
       │ j_1  │         │ j_2  │
       └──────┘         └──────┘
         ↑↓                ↑↓
       ┌──────┐ ←─────→ ┌──────┐
       │ j_3  │         │ j_4  │
       └──────┘         └──────┘
```

Federation 不是 entity——它是 emergent pattern of bridges。

**No federation registry**:

间不提供 "list of federated jians" service。每个 jian 知道自己 connect 到哪些 peers(通过它持有的 bridge capabilities)。"the federation" 不能从某个中心查询——只能从某个 jian 出发,traverse capabilities 看到 reachable network。

**Federation evolution**:

- 加入 federation:跟某个 member jian 建立 bridge
- 离开 federation:revoke 所有 outgoing bridges
- Partial federation:不同 jians connect 不同 subsets,no requirement to "fully connect"

### Identity Continuity

Actor identity 在 间 中是 jian-relative。但实践中我们经常需要"同一个 actor 在多个 jians 中"的 notion——我在公司间和家间都是同一个 person。如何 implement?

**Worldline coherence through capability chains**:

```
Conceptual identity (e.g., "Ren"):
   ↓ has root identity actor
   root_actor_R
   ↓ presents persona in jian j_company
   persona_R_in_company (forwarder to root_actor_R)
   ↓ presents persona in jian j_home
   persona_R_in_home (forwarder to root_actor_R)
   ↓ presents persona in jian j_friends
   persona_R_in_friends (forwarder to root_actor_R)
```

每个 jian 中我有不同 persona(不同 capability、不同 visibility),但所有 personas 通过 capability chain 链接到 root identity actor。

**Verification**:

"persona_R_in_company 和 persona_R_in_home 是同一个人"通过 capability proof 验证:

1. Verifier challenges:发 message 给两个 personas,各自 forward 到 root,root 用 cryptographic signature response
2. Verifier 比较 signatures:相同 root → same identity

注意 root_actor_R **不是 global registry**——它是 actor in some jian(通常是 personal "self jian" 或 trusted parent jian)。Verification 不是查询中央数据库,是 capability-mediated cryptographic proof。

**No global ID**:

间架构 deliberately 没有 global ID system(no DID-as-substrate,no blockchain-as-identity)。Identity 通过 capability chain 维持,worldline coherence 通过 verification protocol 验证。这跟"identity is relational pattern not substance" commitment 一致。

**Privacy implication**:

不同 jian 中的 persona 不需要 expose 自己 link 到 same root。Linkability 是 capability disclosure choice。Default 应当是 unlinkable——only when someone needs to verify "same person",capability 才 expose。

## 六、L4:应用层

L4 是 applications——具体 systems built on 间。这是 architecture 中最 thin 的层,因为 architecture 不规定 application 长什么样。但 L4 的姿态值得说几句。

### 间 application 的 character

一个 "在间上"的 application 不是普通 application 加上 间 SDK——它的 architecture itself reflects 间 ontology:

- 不是 client-server,是 actors-in-jian
- 不是 data store + business logic,是 jians with internal autopoiesis
- 不是 RPC calls,是 capability-mediated message passing
- 不是 user accounts,是 personas with worldline coherence
- 不是 admin panel,是 reflexive jian capabilities

如果某个 application 只是"用 actor model 实现了 client-server",它没有 in 间 ontology——它只是 borrowed actor primitive,没 honor 间 commitments。

### Examples

具体 example application 会 in《器》或 reference implementation 文档,这里只 sketch:

- **Community network (706)**:主 jian = community,members 是 actors in jian,sub-jians 是 events / projects / sub-groups。Cross-community federation 通过 bridges。
- **Agent orchestration (OpenClaw)**:一个 task 是 jian,participating agents 是 actors in jian,tool capabilities 是 attenuated forwarders,task history 是 jian's event store。
- **Payment infrastructure (Nomad OS)**:一个 transaction 是 jian,payer / payee / payment processor / regulator 是 actors,settlement protocol 是 jian's protocol behavior。

这些不是 architectures of these applications——他们是 sketches of how application's architecture maps onto 间 architecture。具体 design 是 application 自己的事。

## 七、Failure & evolution

Distributed systems 的 hardest problems 是 partial failure 和 ongoing evolution。间 architecture 在这两方面有 specific stances。

### Actor 死亡

L1 actor runtime 处理 actor crash。间-specific handling:

- **持有 dead actor capability 的 actors**:next message 收到 capability error。期望它们处理(retry、failover、graceful degradation)。
- **Dead actor 的 history**:仍存在(history 不与 actor 共死,event store 是 jian-level)。
- **Supervision**:linked actors 收到 notification。Standard actor model behavior。

### Jian 解体

跟 §四 描述一致——dissolution 是 reduction 的一种,不是 catastrophic event。
关键在于 dissolution 的 graceful 性:

- 有 prehension chain 维持 history
- 内部 actors 释放回 parent
- Bridge capabilities 自动 revoke

如果 dissolution 不 graceful(比如 process crash 直接 kill jian),需要 supervision protocol 让 parent jian 进入 "child crashed unexpectedly" branch,做 best-effort cleanup。

### 网络 partition

跨 jian bridge 在 partition 时:

- Bridge_actor 收到 message timeout
- 各自 jian 继续 autopoietic existence(local activity 不依赖 bridge)
- Reconnection 时 re-negotiate

注意:partition 期间各 jian 的 state 可能 diverge(如果 application 在两边都有写入)。Reconciliation 是 application-level concern——间 architecture 不 prescribe specific strategy(CRDT、operational transformation、last-write-wins、manual merge)。

### 演化与迁移

Jian 的 behavior `B_j` 可以 update via `become`:

- New behavior 在下个 message processing 生效
- 旧 events in history 不变(history 是 immutable)
- 新 events 由 new behavior 处理

**Schema evolution**:

如果 jian 内部 events 的 content schema 变化:

- Old events 保持 old schema(immutable)
- Reading old events 需要 schema 版本识别
- 通常每个 event 携带 schema version

间架构不强制 specific schema evolution strategy,但 commit 到:**old events 不能 retroactively rewritten**。这是 history 不可变 commitment——你不能修改过去发生的事,只能在新 events 中 acknowledge / reinterpret 过去。

**No system-wide upgrade**:

每个 jian 独立 evolve。Federation 中不同 jians 可以 run different versions——bridges 必须 handle version differences(协商通用 message formats)。这跟 sovereignty commitment 一致——upgrade 不是 imposed by central authority。

## 八、Observability

间 architecture 中 observability 是 perspectival:每个 observer 有自己 view,无 global vantage point。

### 监控架构

```
Per-jian self-monitoring:
  - jian's autopoiesis monitor (already in L2)
  - jian's reflexive capabilities expose health metrics
  
Cross-jian monitoring:
  - monitoring jian holds bridges to monitored jians
  - it queries through these bridges
  - it has its own perspective, not "the truth"
```

注意:monitoring jian **本身是 jian**,有自己的 boundary、history、autopoiesis。它不是 outside system 的 observer。

### Health metrics

Per-jian:

- **Autopoiesis health**:alive 状态、recent activity rate、internal actor count、event creation rate
- **Boundary health**:caveat evaluation success rate、blocked attempts、active bridges count
- **Internal health**:internal actor failure rate、message backlog、resource usage

跨 jian:

- **Bridge health**:message round-trip time、message loss rate、reconnection frequency
- **Federation reachability**:from observer's perspective,what jians are reachable

**No global "system health"**:

监控仪表板可以聚合 multiple perspectives,但 aggregation 是 from monitoring jian 的视角,不是 from outside the system。看到不同 perspectives 都是 valid——两个 monitoring jians 看到不同 picture 是 expected,不是 inconsistency bug。

### Tracing

Distributed tracing 通过 prehension graph:

- 每个 event 携带 prehension(知道 causal predecessors)
- 跨 jian 通过 capability traversal
- Trace 从某个 starting event 出发,反向 walk prehension chain

**Trace 不是 linear timeline**——trace 是 DAG。Visualization 工具需要 handle DAG,而不是 force linear。

### Debugging

间 中 debug 的姿态:

- **Local debug**:在某个 jian 中 query event store、replay events、inspect actor state
- **Cross-jian debug**:bridge to relevant jians、query through capability、stitch perspectives
- **No "step through the system"**:没有 global execution to step through

这听起来 debug 更难,但实际上 force 工程师面对 distributed reality 的真相——distributed system 一直就是 perspectival,假装有 global step-through 才是 illusion。

## 九、Performance & tradeoffs

### 不可妥协的(paradigm-level)

这些是 invariants,implementation 必须 honor 否则它不再是间的 implementation:

- 没有 global state
- 没有 ambient authority
- 没有 universal observer
- Capability discipline(no name forging)
- 涌现性 predicates(not stored)
- Per-jian autopoiesis
- Per-event prehension

violating 任一条 = no longer 间。

### 可调的(architecture level)

这些是 architecture choices,implementation 可以选:

- L1 actor runtime 的 specific 实现
- Storage backend(memory、log、SQL、KV、graph)
- Network protocol
- Scheduling 策略
- τ window per jian type
- GC 策略

### 可优化的(parameter level)

最低优先级 optimizations:

- Message routing latency
- Memory footprint
- Cache strategies
- Connection pooling

这些可以 aggressive 优化,只要不 violate above。

### Tradeoff 思考

**Latency vs paradigm purity**:

间的 capability-mediated cross-boundary message 比 direct shared memory 慢。如果 application 极度 latency-sensitive,architectural temptation 是允许 fast path bypassing capabilities。**Resist this**——一旦允许,paradigm 就开始崩。如果 application 真的需要 sub-millisecond shared-memory speed,它可能不应当用间——it's the wrong paradigm for that workload。

**Memory vs history retention**:

完整 history 是 expensive。Tiered storage(hot in memory、warm on SSD、cold archived)是 standard answer。每个 jian 自己决定 tiering 策略。

**Liveness check overhead**:

频繁 alive check 增加 overhead。但 too lazy 检查会让 dead jians 长期占用资源。Heuristic: τ-related frequency,长 τ jian 检查 frequency 低,短 τ jian 检查 frequency 高。

**Bridge maintenance**:

每个 bridge 有 cost(capability 持有、health check、reconnection logic)。Federation 太密会让 bridge cost 主导。设计 federation topology 时考虑 sparse bridges,通过几个 well-connected jians 实现 transitive reachability。

### 性能的本体论限度

值得 explicit:间 architecture 不是 universally most performant solution。它在某些维度 trade performance for ontological correctness——specifically:

- 关系性 over 实体性:capability indirection cost
- Per-jian sovereignty over central efficiency:no global optimizations
- Perspectival truth over single source: replicated state cost
- Autopoietic dynamism over static structure:liveness check overhead

如果某个 use case 不 share 这些 commitments(比如纯 numerical computation、no inter-actor coordination needed),间 是 unnecessarily 重的。间 的 sweet spot 是 cooperative infrastructure、coordination-heavy systems、relational reality——在这些场景中 paradigm correctness 的 value 远超 performance overhead。

## 收

到这里 architecture 的 core 立住了。

它 honor 了《理》《气》《式》:

- 五层架构对应间的 ontological 层次,L0 到 L4 是从 substrate 到 application 的自然 layering
- L1 actor 基底是普通的,L2 才是间-specific,这个分离让 L1 可以选成熟 runtime 而不影响 L2 的 commitments
- L2 的四 sub-components(jian、capability、event store、autopoiesis monitor)各自 implement 一组 JC invariants
- L3 共生层 implement structural coupling、no merge / no hierarchy
- 没有 global state layer、central control layer、universal monitoring layer——这些 omissions 不是 failure,是 deliberate exclusions
- Failure handling、observability、performance 都 perspectival、distributed、per-jian

它 leaves open(deliberately):

- 具体语言、runtime、storage、网络协议
- 具体调度策略、GC 策略
- 具体 schema evolution 策略
- 具体 federation topology
- 具体 reconciliation 策略

这些是 implementation choices,不是 architecture commitments。

**协议(C)**:跨 implementation 的 wire-level protocols。两个 different implementations 的 jians 如何 talk——具体 message format、capability proof format、bridge negotiation protocol、event reference cross-implementation format。

**模式语言(F)**:常见 patterns——membrane、sealer、saga、attenuated capability、structural coupling 的不同 form。这是 working with 间 的 vocabulary。
