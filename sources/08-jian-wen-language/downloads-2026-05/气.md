# 气

> 理者气之理,气者理之气。
> 离气无理,离理无气。

---

## 起

《理》立了根基。这份文档接续《理》,做一件事:把理的每一个 commitment 翻译成工程的具体姿态,让工程不偏离理,让理可以被工程 incarnate。

这份文档不是工程指南,不是 specification,不是 implementation guide——这些是后续文档的事。这份文档是**对应表**:理中的每一个核心概念,在工程中应当显现为什么形态,**且不应当**被误读为什么形态。每一条 commitment 都包含 mapping(映射)和 must-not(不可还原)两面——前者说理如何下贯到器,后者守护理在器中不被悄悄 substantivized。

理与气不二。这份文档不是从理派生出工程,这份文档是同一个 reality 的工程显现的 articulation。

---

## 一、核心范畴的工程对应

理的根本范畴——间、事/actor、机/event、心、理本身——每一个在工程中都有对应的具体形态。但这些对应不是 1-to-1 的 reduction,是同一个 reality 在工程 register 下的显现。每一项需要同时说明 "shows up as" 和 "must not be confused with"。

### 间(Jian)

**显现为**:一类 first-class actor,带 mandatory 的 reflexive capabilities——它能够 query 自身(谁在我之中、发生过什么、我与父间的关系)、modify 自身(接受新成员、改变 visibility)、observe 自身的 ongoing dynamics。每个 jian 是 first-class entity,有 stable address,可以被 reference、被 message、被 nested。

**不应被误读为**:
- 不是 container —— 没有"actors stored inside jian"的关系。Jian 与其内部 actors 的关系是 ongoing 的 mutual constitution,不是 has-a。
- 不是 namespace —— jian 不是 actors 的命名 scope,是 actors 得以为 actors 的关系场域。
- 不是 group —— jian 不是成员的 collection,jian 是成员之间互动的 emergent unity。
- 不是 session —— jian 不只是协议的载体,jian 也是空间的载体;session-only reading 丢了空间维度,space-only reading 丢了时间维度。

工程上的 telltale 区别:如果你的代码可以"创建一个空 jian",然后"往 jian 里加 actors"——这是 container 思维,违反间的 ontology。正确的姿态:jian 是在 actors 即将互动时 spawn 出来的,jian 的诞生跟它的第一次内部互动是同一件事。

### 事(Actor)

**显现为**:标准 actor——有 mailbox、有 private state、有 behavior(从接收消息到 spawn / send / become 的 function)、有 lifecycle(spawn → live → die)。Actor 之间通过 async message passing 交互,no shared memory。

**不应被误读为**:
- 不是 object —— object 有方法被外部调用,actor 只 receive messages。这个区别 ontologically 关键:object 模型隐含"外部 caller 控制 object",actor 模型 honor "actor 自主决定如何 respond"。
- 不是 process with global identity —— actor 没有 jian-independent 的 identity。同一个 actor 在不同 jian 中是不同 personas,身份是 jian-relative 的 worldline。
- 不是 substance with attributes —— actor 的 state 不是 attribute store。State 是 actor 在它的 worldline 上累积下来的 history 的当下 fold。

工程上的 telltale 区别:如果你想给 actor 一个 "global ID" 让它跨 jian 被一致引用——这是 substance 思维。正确的姿态:actor 在每个 jian 中获得一个 jian-local handle,handle 之间的"是同一个 actor"的关系是通过 capability chain 维持的,不是通过 global registry。

### 机(Event / Occasion)

**显现为**:first-class entity,不只是 message in transit。每个 event 是一次 actual occasion——它有自己的 identity、它显式 reference 它的 causal predecessors(prehension)、它在被某个 actor "处理" 后并未消失而是成为 jian 的 history 的 part。

**不应被误读为**:
- 不是 transient message —— 消息送达后即消失这是传统 actor 模型的 implementation detail,不是 ontology。机一旦发生,即成为 reality 的 permanent part,继续 prehended by 后续 events。
- 不是 log entry —— event 不是事后的"记录",event 就是发生本身的 first-class form。
- 不是 trigger —— event 不只是触发后续 action 的 cause,event 是当下 reality 的具体化。

工程上的 telltale 区别:如果你的系统中"消息处理完就 garbage collected"——这违反机的 ontology。正确的姿态:events 进入 jian 的 history,可以被后续 events prehend、被 jian 的 query 检索、被嵌套 jian 的 events 引用。Event sourcing 不是 architectural choice,是 ontological commitment。

### 心(Mind)

**显现为**:**双面**。
- 作为间的反身性:每个 jian 暴露 introspection capabilities——能 query 自己的 membership、history、boundary、visibility,能 reason about 自己的 state。这是 first-class 的、reified 的、可被 programmed against 的能力。
- 作为 actor 的当下:**没有对应的 first-class API**。Actor 的 immediacy、agency、awareness 不被 represent 为 data structure 或 capability。它在 actor 的 ongoing 互动中 enacted,但从不被 stored、queried、或 manipulated。

**不应被误读为**:
- 不是 consciousness module —— 心不是某个 actor 内部的子组件。任何把"心"做成 actor's internal state field 或 capability 的尝试都是 reification 错误。
- 不是 metadata —— actor 的 immediacy 不是关于 actor 的元数据。元数据是 about something,immediacy 不是 about,immediacy 就是 being itself。

工程上的 telltale 纪律:**间可以 reify 它的反身性,actor 不可以 reify 它的当下性**。前者给系统 self-awareness,后者保护 actor 的 ontological integrity。如果你想给 actor 加一个 "consciousness" field——停下,这违反根基。

### 理(Li)

**显现为**:跨 jian 的 invariants——同样的间-actor-事不二、同样的关系本体、同样的涌现模式,在每一个 deployment 中以同样的方式 hold。这些 invariants 不是 enforced by central authority,是通过每个 jian 的 internal structure 自然 instantiate 的。

**不应被误读为**:
- 不是 schema —— 理不是 data schema,不是 structural definition that deployments must conform to。理是每个 deployment 自己生成的 coherence pattern。
- 不是 protocol standard —— 理不是某个外部 spec 文档,理是间的 internal logic 的 emergent character。
- 不是 governance rule —— 理不是被 imposed on deployments 的 rules,理是 deployments 因其本性而自然 honor 的 pattern。

工程上的 telltale 区别:不存在"理的 enforcement engine"。如果一个 deployment 不 honor 理(比如它实现了 jian 但把 jian 当 container 用),它不会被某个 central authority 拒绝,它只是自己滑出了间的 family——它仍然 work 但不再是 jian。理通过 self-coherence 维持,不通过 enforcement 维持。

## 二、涌现性 commitments

理的一个核心 commitment 是:**间的"属性"不是 stored attributes,是关系状态的 emergent expression**。这条 commitment 在工程上落实为一组严格的 derived-not-stored 规则。每一项都需要工程师抗拒"把它做成 first-class field"的本能冲动。

### Caveat 是 derived,不是 stored

**正确**:每个 jian 的 caveat(谁可以加入、什么 events 合法、什么操作允许)是从 jian 内部 actors 的 capability graph + ongoing interaction patterns derive 出来的。当一个外部 actor 试图加入,jian 的 response 是当下计算的——基于现有成员的 capability、当下的 interaction state、可能涉及的成员协商。

**错误**:在 jian 上挂一个 `caveat: AccessRule[]` field,加 actor 时检查这个 list。

**违反代价**:把 caveat reify 成 stored field,等于把"这个间是什么样的间"从关系动态变成了 substance attribute。后续所有"修改 caveat" API 都进一步 substantivize,最终系统从关系本体论滑回实体本体论,所有从理推出的 properties(autopoiesis、structural coupling、leverage 性质)都失效。

**工程实现路径**:caveat 通过 actor-level capability composition 实现。一个 actor 持有"加入此 jian"的 capability,这个 capability 本身是 forwarder actor,它在被调用时 evaluates 当下条件——这个 evaluation 就是 caveat 的 emergent form。

### Visibility 是 derived,不是 stored

**正确**:从 jian 外部能观察到 jian 内部什么,取决于观察者持有的 capability 在 jian 的 capability graph 中能 reach 到什么。Visibility 是 capability 拓扑的 emergent property。

**错误**:在 jian 上挂一个 `visibility: PolicyConfig` field,定义谁能看到什么。

**违反代价**:visibility config 把"谁看到什么"从 capability 拓扑的 truth 变成了管理员的 declaration。两者可能在 happy path 一致,但在 corner case(capability 被传递、被 attenuated、被 revoked)上 diverge。Stored config 不会自动跟上,必须手动同步——这种手动同步本身就是 substance 思维的症状。

**工程实现路径**:观察者要 query jian 的某个方面,实际上是发送一个 message;这个 message 是否 succeed 取决于观察者的 capability 能否 traverse 到那个 query 点。没有"被定义的 visibility",只有"capability 实际上能 reach 的范围"。

### Protocol legitimacy 是 derived,不是 stored

**正确**:某个 message 在某个 jian 中是否合法(合于协议的下一步、合于当前 interaction state),是从 jian 内部 actors 的 ongoing interaction history 当下判断的。每个 actor 根据自己的 session-actor 当下 state 决定接受或拒绝。

**错误**:在 jian 中存一个 `current_protocol_state: StateMachine` 全局变量,每个 message 来时 check + update。

**违反代价**:中心化的 protocol state 假设有"间的视角"——某个 omniscient observer 知道协议进行到哪一步。但《理》明确说没有间外的观察。Protocol state 必须是 distributed across actors,每个 actor 有自己的 view,collectively 形成 protocol 的 ongoing reality。

**工程实现路径**:multiparty session types 投影到每个 actor 的 local session-actor。Local session-actor 是 stateful 的,但它的 state 是它自己的 view 不是间的 view。间的 protocol 是 actors 各自 view 的 emergent coherence。

### Jian boundary 是 derived,不是 stored

**正确**:jian 的边界——什么 actors 在内、什么在外——是从 actors 的 ongoing 互动活动 derive 出来的。一个 actor 在 jian 中,是因为它正在 participate in jian 的内部互动;它一旦停止互动(超过某个 timeout、或显式 leave),它就不再在 jian 中。

**错误**:在 jian 上挂一个 `members: Set[ActorRef]` 列表,join/leave 操作显式增删。

**违反代价**:stored membership list 把 jian 变回 container,违反 autopoiesis——jian 应当通过 ongoing activity 维持自身,不通过 stored state。Stored list 还引发"membership 跟实际互动 inconsistent"的可能性,这种 inconsistency 在关系本体论下是 incoherent 的。

**工程实现路径**:membership 是 active liveness 的 function——actor 通过 heartbeat / activity / participation 维持它在 jian 中的 presence,中断则自动脱离。这跟 Erlang 的 link / monitor 思路一致但 deeper:不只是 actor 的存活,是 actor 在 jian 中的活跃。

### 通则:涌现 vs stored 的判断标准

任何工程概念,问自己:

- 它是关系状态的 expression,还是独立的 storage?
- 它是 ongoing activity 的 product,还是 once-set-then-static?
- 它能从其他东西 derive,还是必须独立维护?
- 修改它需要修改关系本身,还是可以单独修改它?

如果答案偏向后者,这个概念被错误 reified 了。重新设计。

## 三、Reify / Non-reify 边界

承上,"什么可以被 reify 成 first-class entity、什么不可以"是间工程的一条根本纪律。这条纪律不是 stylistic preference,是 ontological commitment 的工程表达。

### 可以 reify 的

**间** —— 因为间有反身性。间作为 first-class actor 让系统能够 reason about jian、嵌套 jian、传递 jian-references。Reifying jian 是 honoring 它的 ontological integrity,不是 substantivizing 它。

**事/Actor** —— Actor 是 already 个体化的实体,reify 是它的本性。注意:reify actor 不是 reify "actor 的 substance",是 reify "actor 这个 individuation 点"——actor 的 internal state 仍然是它 worldline 的 fold,不是 attribute bundle。

**机/Event** —— 每个 event 是 actual occasion,有 identity 和 prehension 关系,first-class 是它的本性。

**Capability** —— Capability 作为 forwarder actor 是 reified 的,因为它本身就是 actor。但 capability 不应被 reify 成 "permission record"——这又滑回 stored attribute。

**Session** —— Session-actor 是 reified 的(因为它是 actor),但 session 的 protocol state 应当是 actor 内部的 emergent state,不是 external 的 state machine config。

### 不可以 reify 的

**心(actor 当下面)** —— 已论。Actor 的 immediacy / agency / awareness 没有对应数据结构。

**关系本身** —— 关系不是 entity,关系是 actors 之间的 ongoing interaction。试图把 "the relationship between A and B" 做成一个 entity (比如 `Relationship(A, B, type, ...)` record)——这是 reification 错误。关系通过 actors 之间的 ongoing message exchange enacted,通过 capability graph manifested,但本身没有 first-class form。

**理** —— 理是 cross-jian invariant pattern,不是 stored entity。试图把"理"做成 schema、做成 enforcement engine、做成 governance contract——都是 reification 错误。理通过每个 jian 的 self-coherence 维持。

**Cosmic 间** —— Cosmic 间是 ontological ground,不是工程实体。没有 master node、没有 root registry、没有 universal cluster。任何具体 deployment 都是 local jian,cosmic 间通过 deployments 各自 honor 同一个理而 implicit present。

**身份(actor 的 substantive identity)** —— Actor 在跨 jian 的"是同一个 actor"是 worldline coherence,不是 identity record。试图把这个 coherence reify 成 global ID / DID / blockchain identity——这是 substance 思维。Coherence 通过 capability chain 维持。

### 通则:reify 判断标准

任何工程概念,问自己:

- 它是 individuated entity(有自身的 boundary、agency、history)吗?如是,可 reify。
- 它是 ongoing activity 的 mode 或 pattern 吗?如是,不可 reify。
- 它是关系或关系的 character 吗?如是,不可 reify(应通过 actors 间的 interaction enact)。
- 它是范畴或概念的 instance 吗?Reify instance 可以,reify 范畴本身不行。

模糊地带 default to **不 reify**。Reification 一旦做错,后续修复极难,因为整个系统的其他部分会 build on top of 错误的 reification。Non-reify 是 conservative 的安全选择。

## 四、动静不二的工程表达

理 commits to 动静不二——state 和 event 不是两个 primitives,是同一个 spatiotemporal reality 的不同 projection。这条 commitment 在工程上有具体的 design implications。

### 双 view 必须并存

每个 jian 必须同时支持两种 query:

- **Spatial slice**: "现在 jian 的 state 是什么"——给出当下 membership、active capabilities、derived caveat、当前 protocol position 等的 snapshot。这是 state view。
- **Temporal slice**: "jian 是如何到达现在的"——给出 events 序列、causal graph、关键 transitions 的 history。这是 event view。

**不允许**:只支持其中一个 view 的 jian。这违反动静不二——把 reality 偏到动或静的一面。

### State 是 events 的 fold

实现上,state 不是独立维护的,是 events 的 deterministic fold。给定一个 jian 的 events history,它的 state 是 calculable 的——从 initial state 起,顺序 apply 每个 event 的 effect,得到当下 state。

这等价于 event sourcing,但 ontological grounding 不同:event sourcing 通常是 architectural choice(为了 audit、replay、debugging),间中是 ontological commitment(state 不是独立 reality,是 events 的 derivative)。

工程上含义:
- Events 是 source of truth,state 是 cache。
- State snapshot 可以 take(为了性能),但必须可以从 events rebuild。
- "改变 state" 这件事 ontologically 不存在——只有 "新 event 发生,导致 derived state 改变"。

### Event 包含 prehension

每个 event 显式 reference 它 prehend 的 predecessors。这是 Whitehead 的 prehension 在工程上的具体化:

- 每个 event 知道它的 causal parents。
- 每个 event 知道它发生时的 jian state(implicit through parents)。
- 每个 event 是 "given this past, this is what now arose" 的具体化。

这不只是 metadata。Prehension 让间的 history 不是平坦的 timeline,而是有内部 causal structure 的 graph。这个 graph 是 jian 的真正 history,linear timeline 只是它的一个投影。

### 没有 "current state" 的特权

工程上常见错误:认为"当下 state"是 jian 的 essential reality,events 只是历史记录。

间的纪律:**没有"current"的特权**。任何时刻都是 spatiotemporal reality 的某个观察 cross-section。"当下"对一个观察者是这一刻,对 nested jian 中的 actor 可能是另一刻,在跨 jian 的 causal graph 中根本没有 universal "now"。

这跟广义相对论的 simultaneity 相对性同构。工程含义:
- 不要假设 global clock。
- 不要假设 universal "current state"。
- Causal ordering(prehension graph)是 reliable 的,linear time ordering 不是。

## 五、Autopoiesis 的工程要求

间作为自创生系统,有具体的工程要求。这些要求不是 implementation detail,是间作为间的 defining features。

### Jian 的存在 = ongoing activity

一个 jian 存在,iff 它的内部 actors 在 ongoing 互动。互动停止,jian dissolve——不是"被删除",是它本来作为 process 的存在终止了。

工程实现:
- Jian 不是 stored record,是 active process。
- Jian 的存活通过 internal heartbeat / activity 维持。
- 长时间无 activity 的 jian 自然 dissolve,留下 history(events 仍然 reachable through parent jian)但 jian 本身不再 active。

这跟 Erlang 的 process 哲学共振,但 deeper:不只是 actor 是 process,jian 也是 process。

### Jian 的 boundary 是运作的 product

Boundary 不是预先 specified 的——它是 actors 在 jian 中的互动 itself 持续生产的。

具体地:
- 谁 in / 谁 out,通过谁 actively participate / 谁 disengaged 决定。
- 什么互动 in / 什么 out,通过 ongoing capability composition 决定。
- 什么 visible / invisible,通过 ongoing capability traversal 决定。

工程含义:
- 没有 "set jian boundary" API。
- 通过 actors 的 capability 关系来 shape boundary。
- Boundary changes 是 ongoing capability dynamics 的 emergent consequence。

### Jian 的健康度量

Autopoiesis 给了 jian "健康"的精确 criteria:

- **正在维持自身**吗——内部 actors 在 ongoing 互动?
- **正在生产 components**吗——新的 actors / events / capabilities 在 emerging?
- **正在跟环境保持 productive coupling**吗——跟父 jian / 邻 jian 有 active 但 sustainable 的 message exchange?

不健康的 patterns:
- **凝固**:state 长期不变化(没有 ongoing activity 维持)。
- **耗散**:活动但没有 coherence(activity 不在 maintain jian 的 identity)。
- **自闭**:跟环境 zero coupling(没有 productive 的 cross-jian interaction)。

工程上的 monitoring 应当 measure 这些 autopoietic dimensions,不只是 message rate / latency 这些表层 metrics。

### 间不是 created,是 spawn

工程语汇上的细节但 ontologically 重要:不要说 "create a jian",说 "spawn a jian"。Create 暗示 substance(creator 制造 created),spawn 暗示 process(activity 生成 new activity)。

具体地:
- 一个 actor 通过执行某个 action(初始化 internal interaction)spawn 出一个 jian。
- Jian 一旦 spawn,它的存在跟 spawning actor 解耦——spawning actor die 不影响 jian。
- Jian 的存活由它内部 ongoing activity 维持。

## 六、结构耦合作为 cooperation 的形式

理 commits to:间间连接的唯一形式是 structural coupling,不是 merge / hierarchy / control。这给 federation、interoperability、cross-deployment 一个精确的工程姿态。

### 两个间的连接 ≠ merge

当两个独立 deployment 建立 bridge,它们 do not become one super-deployment。每个 jian 仍然 self-maintaining,有自己的 autopoiesis,有自己的 boundary,有自己的 history。

工程实现:
- Bridge 是 capability exchange,不是 state merge。
- Bridge 不创建 shared state,创建 ongoing message channel between 两个 sovereignty。
- 各 jian 的 internal state 仍然 internal。

### 两个间的连接 ≠ hierarchy

没有"主-从"connection。Bridge 是 symmetric 的——两边都是 sovereign,都可以 propose interaction、都可以 retract、都可以 evolve their own coupling stance。

例外:嵌套 jian 跟 parent jian 有 hierarchical 关系,但这是 ontological 嵌套,不是 cooperative connection。两个 sibling jian(同一 parent 的子 jian)之间也没有 hierarchy,它们是 sibling sovereign。

### 两个间的连接 = mutually responsive

Structural coupling 的正面定义:两个 jian 在 ongoing 运作中变得 mutually responsive。一方的内部 activity 影响另一方(通过 bridge messages),另一方的 response 又影响第一方,形成 cross-jian feedback loop。

这个 feedback loop 不是控制——双方都不"控制"对方,各自 self-maintain。但它们的运作变得 historically intertwined,各自的 evolution 反映对方的 presence。

工程含义:
- Cross-jian protocol 应当是 symmetric 的(两边都可以 initiate、retract、evolve)。
- Cross-jian state 不存在(没有 shared state),只有 cross-jian message history。
- Cross-jian coupling 的"健康"通过双方各自的 autopoiesis 健康衡量,不通过 coupling 本身的某个 metric。

### Bridge 的 capability 形式

具体形式:每个 jian 颁发 attenuated capability 给对方,对方 actor 持有这个 capability 跟此 jian interact。Capability 本身是 forwarder actor,所以 bridge 是 actor-mediated。

Capability 可以被 attenuated(降低权限)、被 revoked(终止 coupling)、被 delegated(传递给第三方但带 caveat)。这给 cross-jian relationship 一个 fine-grained 的演化空间。

### Federation 不是 union

多个 deployment 形成 federation(比如多个 community network 互相承认成员),工程上**不应**实现为 union of states / shared registry。

正确实现:每个 deployment 维持自己的 membership,通过 capability exchange 跟其他 deployment establish bridges。一个 actor 作为 "federated member" 是它在多个 jian 中各自有 active capability 的 emergent状态,不是它在某个 federation registry 里有 entry 的 stored fact。

## 七、二阶控制论的工程纪律

理 commits to:没有间外的观察,所有视角都是 perspectival。这条 commitment 给出一系列工程纪律。

### 没有 universal observer

具体禁止:
- 不应有 global state store。
- 不应有 central monitoring service that "知道一切"。
- 不应有 admin dashboard that 显示 "the system" as a whole。
- 不应有 global event log 可被 totally queried。

这些都是 substance 思维的工程化,假设有 god view。间没有 god view。

### Observation 必须 sourced

任何观察必须有 source jian——观察是从某个 jian 的 perspective 发出的。

工程实现:
- 任何 query 携带 source jian reference。
- Query result 是 source jian 通过它的 capability 能 reach 到的部分,不是 ground truth。
- 不同 source jian 看同一片 reality 可能得到不同 result——这是 feature 不是 bug。

### Monitoring 是 reflexive 的

Monitoring system 自己是 jian。它 observes 其他 jians 是从它自己的 perspective,通过它持有的 capability。它不在 system 之外。

这有具体含义:
- Monitoring jian 也有自己的 boundary、autopoiesis、被 monitored 的可能(meta-monitoring)。
- 没有特权 monitoring——monitoring jian 跟它 monitor 的 jian 是 ontologically peers。
- Monitoring 的失败、偏见、blind spots 是 expected 的——因为 monitoring 不是 god view 而是 perspectival。

### Logging 不是 universal record

每个 jian 的 events 是它自己的 history,reachable through 它自己的 capability。"完整的系统 log"不存在,因为系统不是 unified entity。

工程含义:
- 每个 jian 有自己的 history。
- 跨 jian 的 history correlation 是通过 prehension(events 引用其他 jian 的 events)实现的,不是通过中央 log。
- Audit / forensics 不是"查 system log",是"在多个相关 jians 中各自查它们的 history,通过 prehension 关系拼接"。

### Debugging 是 perspectival

工程师 debug 一个 issue,要明确"我现在从哪个 jian 的 perspective 看",不能假设有客观视角。这听起来像 inconvenience,实际上 forces 工程师面对 distributed system 的真相——distributed reality 一直就是 perspectival,假装有客观视角才是错误。

## 八、杠杆点定位

理给出间的 ethical articulation:间是范式层级的干预,它的存在 itself 改变可能性空间的形状。这个定位有具体的工程含义。

### 不在 parameter level 优化

性能优化是次要的。如果性能 vs paradigm purity 冲突,paradigm 胜。

具体地:
- 不要为了减少 message overhead 而 violate actor model(比如允许 shared memory)。
- 不要为了快速 query 而引入 global state store。
- 不要为了 reduce latency 而 cache things in ways that violate autopoiesis。

性能是 important 的,但是 second-order——在 paradigm 不被 violate 的范围内 optimize。如果某个 optimization requires paradigm violation,放弃这个 optimization。

### 不在 structure level 过度 elegance

具体协议、API、data structure 的优雅是好事,但是 third-order——它服务于 paradigm 的 honored,不为自身。

具体地:
- 不要为了 protocol 的 mathematical elegance 而 force 关系性 reality 进入 substance form。
- 不要为了 type system 的 power 而 reify 不应被 reify 的概念。
- 不要为了 API simplicity 而 hide 关系本体的 truth(比如假装有 global state 让 API 更"简单")。

### 在 paradigm level 严守

最高优先级是 paradigm 的纯粹:关系本体论、autopoiesis、no ambient authority、no universal observer、动静不二、心不被 reify。

具体地:
- 任何 design decision 先问:它是否 honor paradigm?
- 然后再问:它是否 elegant、performant、convenient?
- Tradeoff 时,先于 paradigm 妥协的 design 应当被 redesigned,不是 accepted。

### 在 transcending level 保持开放

Donella Meadows 的最高杠杆点是 "transcending paradigms"——能够意识到任何 paradigm 都是 partial,保持 paradigm 自身被超越的开放。

间的 paradigm 是 powerful 的,但不是 final。工程上的纪律:
- 不要把间的 paradigm 当作 universal solution。
- 在某些场景(比如纯 computational tasks、no inter-actor coordination)substance ontology 可能更 fit——这种时候不要 force jian。
- 间的 value 在 cooperative infrastructure、coordination problems、relational reality——在这些场景中它是 paradigm-level intervention;在其他场景中它是 unnecessarily heavy。

这种自觉让间不变成另一种 totalization,而保持作为 contextual 的范式选择。

## 十、自检清单

任何具体工程决策可以回到这份 checklist:

**关于 reify**:这个新 entity / field / API,是 honoring 某个 individuated reality,还是在 substantivize 某个关系或 mode?

**关于 storage**:这个被 stored 的东西,本应是 derived 还是 stored?如果是 derived 但被 stored 了——重新设计。

**关于 observer**:这个 query / observation,有 explicit 的 source jian 吗?还是隐含假设了 god view?

**关于 boundary**:这个 boundary 是 ongoing activity 维持的,还是 set-then-static?

**关于 coupling**:这个 cross-jian connection,保持双方 sovereignty 吗?还是 merge / hierarchy?

**关于 paradigm**:这个 design 服务于 paradigm 的 honor,还是为了 convenience 而 violate paradigm?

**关于 心**:这个 design 是否试图 reify 某种 awareness / agency / immediacy?如是,reconsider。

如果某个决策在多个 check 上 fail,这不是"实用主义 vs 理论纯粹"的 tradeoff——这是 design 偏离了根基。回到《理》,重新审视,redesign。
