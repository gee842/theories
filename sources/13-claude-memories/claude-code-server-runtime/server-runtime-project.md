Ren 在 `/Users/ren/server/runtime` 构建个人 server 的"浏览器操作系统"：独立 web dashboard（shell），单次 passkey 登录进入可增长的 app 列表（Terminal / Editor / Desktop / Host / Hello 示例），未来 agent UI、files、host-admin。**这是 Ren 与 server 交互的主 UI**——可靠性与恢复路径一等（SSH 永远独立于本系统）。北极星：加新 app 必须便宜。未来开放给朋友（multi-user schema 第一天建模，邀请制）。

**Why:** 架构决策是与 Ren 多轮确认的结果，后续实现不可擅自偏离。
**How to apply:** 以 repo 的 `PLAN.md`（v4 完整版，含 Status 行）为计划，`docs/`（architecture / invariants / add-an-app / deploy / recovery / acceptance / desktop / host-target）为已建成系统的事实；`README.md` 是入口。改动先对照 `docs/invariants.md` 16 条。

关键架构（已实现）：Caddy 唯一公网入口 + forward_auth → authd（唯一 authz 点）；每 app 独立子域 + `__Host-rt_<app>` cookie；`/__runtime/*` 静默换票（state 绑定）；authd 挂 os 域；内部上游全 unix socket（`/run/runtime/<target>/`，setgid `runtime-sock` 组）；workspace = rootless Podman + systemd PID1；自写 daemon 走挂载交付 `/opt/runtime/units` + `runtime-link-units`（不重建镜像不杀进程，KillMode=process）；registry（`packages/registry`）唯一真理源 → `pnpm gen` 产出 Caddyfile/Quadlet/units/env/authd 配置（生成物提交，`gen --check` 防漂移）；`pnpm new-app <id> [--daemon]` 脚手架（KPI 实测 14 秒到 dashboard 可用）。

**2026-08-22 交付 Status app**（PLAN §21.5 只读半边，`20a3922` + `293eac6`）：`status.datong.to` 渲染 `doctor.sh --json`。关键设计：**无 daemon** —— systemd socket 激活（`runtime-doctor.socket` + `@.service`），每连接跑一次 `status-response.sh`，它**只写不读连接**，这是允许 root 程序挂在 web 路由末端的全部理由（写在脚本头、`DaemonSourceSchema`、`docs/status.md` 三处）。registry 因此多了第三种 daemon source `system`。实测：一次 walk 5.8–7.6s / 5.2s CPU，所以改成 answer-first（先发磁盘上的快照、关连接、再走下一次），请求稳定 ~20ms，`X-Runtime-Refreshing` 头驱动页面轮询。

**doctor 性能的教训（2026-08-22, `52c6894`）**：把容器段的逐项 `podman exec` 合并（8+18 次特权调用 → 2+6），真机报告 158 行逐字不变，但一次 walk 只从 ~6.8s 降到 ~4.9s（28%）—— **进程启动不是大头,我预测"能压到 2s 内"是错的**。剩余耗时未 profile,候选:socket 隔离矩阵（每 socket × 每 peer 一次 setpriv,约 40 次）、逐 host 的 DNS/TLS + gateway 往返、backups 段的 `sha256sum --check`（真在哈希备份数据）。**再优化前先给各 section 计时,别再从猜测出发。** 不紧急:answer-first 之后没人等 walk。
