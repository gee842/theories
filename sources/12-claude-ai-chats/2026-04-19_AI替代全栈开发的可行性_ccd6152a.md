**这个 loop 的瓶颈不在 execution,在 objective function。**

## 核心问题:什么叫 "reach objective"?

你说 "if can not reach objective, redo"。但 objective 在软件里是 **under-specified by nature**。

展开讲:

**Level 1 — Functional correctness.** "用户能登录"。这个 AI 能自己判断,写 test,test 过了就是 reached。没问题。

**Level 2 — Non-functional properties.** "系统是 maintainable 的 / architecture 是 clean 的 / 这个抽象是对的"。这些怎么 evaluate?你 spawn 一个 evaluator agent,它用什么 rubric?rubric 本身就是 architectural taste 的 encoding。如果你能写出完整的 rubric,你其实已经做完了 architecture 工作。如果 rubric 是 AI 自己生成的,那 evaluator 和 executor 共享同一个 prior,self-evaluation 会 converge 到 "looks good to AI" 而不是 "looks good to Ren"。

**Level 3 — Product-market fit decisions.** "这个 feature 应该这样 work 还是那样 work"。这里不是 objective 的问题,是 objective 本身就在 evolve。PRD 写的时候你以为要 A,实现到一半市场反馈说 B 更好。autonomous loop 不知道这事,它会忠实地把 A 做完。

## 你的 loop 会收敛到哪里

假设你真的把一切自动化,objective 是 PRD。loop 跑完,你得到:

一个**严格满足 PRD 的系统**。

问题是:PRD 的价值不在于"被精确实现",而在于它是一个 **snapshot of your thinking at t=0**。软件开发的 80% 价值创造发生在"实现过程中你发现 PRD 某个地方是错的"——这个 discovery 被你 optimize 掉了。

更糟的是:AI 遇到 PRD 里的矛盾或模糊时,会**自己 resolve**,而不是停下来让你重审 PRD。resolution 会用 training distribution 的 default。结果是你的 product 慢慢回归到"AI 认为最常见的那种 product",而不是你想做的那个偏门有趣的 product。

这对 OpenClaw 尤其致命,因为 OpenClaw 本身是 novel architecture。SST 的很多决策没有 training prior,AI 会默认往 LangChain / AutoGPT 这种有大量 training data 的方向 drift。你的 loop 跑完,交付物会有一种诡异的"这不是我的 OpenClaw 了"的感觉。

## 更精确的 pushback

不是 "automation 做不到",是 **automation 的 fixed point 是你的 objective function 的 fidelity**。

- 如果 objective function 是 high fidelity(例如 "implement this well-defined RFC"),automation 收敛到你要的东西。
- 如果 objective function 是 low fidelity(例如 "build Nomad OS"),automation 收敛到一个 statistical average of what "Nomad OS" means to the training distribution,不是你脑子里的那个。

**你在中间 intervene 的那 5-10 次,本质是在 continuously refine the objective function**。这个 refinement 不是可选的工程实践,是信息传递的 **最低必要带宽**。切断它,你不是在 offload 工作,你是在 offload product ownership。

## 一个更 honest 的 frame

你真正想要的不是 "automate everything",是 "**把我的介入压缩到只在 high-leverage decision points**"。这两个听起来像,但差一个数量级:

- "Automate everything" = 0 次介入
- "High-leverage only" = 从每天 50 次压到每天 5 次,但**不是 0**

后者可达,且是 Claude Code subagent / Anthropic 的 agentic research 正在 converge 的方向。前者不是不可达,是达到的那天 **objective function 本身必须先被形式化到 PRD 目前不具备的精度**——那个精度的 PRD 基本等于 implementation。

## 可以测试的点

你 OpenClaw 是你自己的 codebase,拿一个真实的 sub-feature 试:strict "写完 PRD 不介入" vs. "PRD + 每天 5 分钟 review"。跑两周,比较交付物。

我的 prediction:strict 版本能交付能跑的东西,但一个月后你会 rewrite 其中 30-50%,因为它不是你的 OpenClaw,是 "AI 对 OpenClaw 的理解"。每天 5 分钟 review 的版本,rewrite 率降到 5-10%。

这个差值就是 **objective function fidelity 的 cost**。你觉得这个 cost 能付得起,那 strict automation 就是对的选择。在 OpenClaw 这种身份强的项目上,我赌你付不起。在某个 CRUD 内部工具上,你绝对付得起,而且应该全自动化。

所以真正的问题不是"能不能全自动",是"**这个项目值不值得你 inject taste**"。答案因项目而异,不是统一的 yes/no。

- **Number 都是估的**。"500M 消息/天 p99 < 300ms"——这个 claim 没有 capacity model 支撑。真正 senior 的 architect 会附一个 Little's Law + 排队论的推导。我没做。
- **我对 WeChat 的实际 internals 知识有限**。我写的 client-authoritative storage、mutual-friend comment visibility 这些是公开信息。但 WeChat 实际的 MMTLS 协议、内部服务拓扑、他们怎么处理春晚红包峰值(每秒几十万 TPS)——这些我不知道,我的"replica"在这些地方其实是**合理的猜测**,不是真的 replica。
- **Mini Program 那部分我给了 pragmatic 方案 (iframe),没给真 runtime**。真 WeChat 是 JSCore + 自定义 DSL,这个 doc 没有认真 tackle。
- **没 surface 的 failure mode 可能更多。** 比如:跨 region 的 message ordering 在 network partition 下会有什么 anomaly?红包在 DB 主从切换时会不会 double-claim?这些我没展开。真 design review 会在这些地方 grill 我。

## 对你 theory 的 data point

你说 "AI 能 fully automate,don't intervene till done"。

这个 doc 在你没 intervene 的情况下产生了,看起来 serious。**但它 serious 到什么程度取决于你 review 它的能力**。

- 一个不懂架构的 reader 会觉得这是 senior deliverable。
- 一个 senior architect 会在 30 分钟内列出 20 个我没想到的问题(payment 的 FX、group chat 的 reader fan-out、WS gateway 的 graceful shutdown、schema migration 策略、红包的 race condition 细节、等等)。

也就是说:**AI 交付的 artifact 的表观质量高于其实际质量,而两者的 gap 只有 domain expert 能看出。**

在 Discord replica 这种 commodity 场景,gap 很小(因为 AI 的 training distribution 就是这类系统)。
在 WeChat 这种 composite + 有 novel 元素的系统,gap 开始明显。
在 OpenClaw 那种真 novel 的系统,gap 会很大——我会写出一个"看起来合理"的东西,但里面充满 unverified assumptions。

这就是我一直试图 pushback 的那个 core point,只是这次用一个具体 artifact 讲清楚了。你决定这个 gap 能不能接受,per project。
