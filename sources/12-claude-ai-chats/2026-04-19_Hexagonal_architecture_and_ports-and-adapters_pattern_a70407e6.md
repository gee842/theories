**ASSISTANT** (2026-04-19T19:26):

 **The Hexagonal Check — a one-page philosophy**

**The principle.** Your system has a *stability gradient*: some things change rarely (the rules of your problem), some things change constantly (the technologies you happen to use this year). Code is hexagonal if dependency arrows point *from* the volatile *toward* the stable, never the reverse.

**The test, in four questions.** A project is hexagonal to the degree that all four answers are yes:

1. **Can you name the core without naming a technology?** If describing what your system *does* requires words like Postgres, Stripe, HTTP, or React, the core and the infrastructure are fused. A hexagonal core can be described entirely in the vocabulary of the problem.

2. **Does the core define the interfaces, and infrastructure implement them?** Ports live in the core, in the core's language ("I need something that can store Payments"). Adapters live outside and conform. If your domain imports `psycopg2` or `stripe.Client`, the arrow is pointing the wrong way.

3. **Can you run the core with everything faked?** Swap every adapter for an in-memory stub — no database, no network, no clock, no external API — and the core should still execute its logic and pass its tests. If you can't, infrastructure has leaked inward.

4. **Is swapping an adapter a leaf change?** Replacing Postgres with DynamoDB, Stripe with Adyen, REST with gRPC, should touch exactly one adapter file and zero core files. If the change ripples into the domain, the boundary is fictional.

**The smell test.** Three failure modes signal the pattern is being cargo-culted rather than applied:

- *Anemic core, fat adapters* — the "domain" is just DTOs and the real logic lives in services that orchestrate infrastructure. You've added folders, not boundaries.
- *Ports that leak their implementation* — a `UserRepository` interface whose method signatures take SQL fragments or return ORM rows. The port's shape betrays what's on the other side.
- *Framework annotations in the core* — Spring, Django, SQLAlchemy, Pydantic validators tied to HTTP. The core now depends on the framework; the framework does not depend on the core.

**The honest disqualifier.** Hexagonal is worth it when *(domain complexity) × (infrastructure uncertainty)* is high. If your "business logic" is `INSERT INTO users`, the pattern is overhead, not architecture. The check isn't "does this project use ports and adapters" — it's "does this project have a core worth protecting, and is it protected."

**One-sentence version.** *A project is hexagonal if you can delete every file outside the core, and the core still compiles, still tests, and still describes the problem in its own words.*
