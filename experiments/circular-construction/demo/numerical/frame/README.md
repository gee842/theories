# Three-dimensional frame experiment

This is a **separate numerical evidence study**, not a structural release
validator connected to the animation. The actual four-post A/B fixture is
represented with six displacement/rotation DOFs per node and twelve-DOF beam
and column elements: axial extension, bending about both local axes, and torsion.
It is not a truss substitute. `solver.py` exposes `solve_request(request)` and
`transfer_gate(request, result, current_revision, current_fingerprint)`; both
return deterministic JSON-compatible dictionaries. NumPy is the only dependency,
already available in the existing numerical venv.

From the demo directory:

```sh
numerical/.venv/bin/python numerical/frame/fixture.py --fixture A
numerical/.venv/bin/python numerical/frame/fixture.py --fixture B
numerical/.venv/bin/python numerical/frame/fixture.py --negative missing-capture-roll
numerical/.venv/bin/python numerical/frame/fixture.py --negative missing-restraint
numerical/.venv/bin/python numerical/frame/fixture.py --negative weak-member
numerical/.venv/bin/python numerical/frame/fixture.py --study --write numerical/frame/fixtures
numerical/.venv/bin/python numerical/frame/solver.py numerical/frame/fixtures/fixture-A-nominal.request.json
numerical/.venv/bin/python -m unittest discover -s numerical/frame -v
```

`--study` regenerates all five request/result pairs, `stale-input.gate.json`
and `study-summary.json` from the current source/contact inputs. An omitted
`--write` with `--study` uses the adjacent `fixtures` directory. The summary is
generated by the same `summarize_case` API used by the single-case CLI.

The solver also accepts stdin and `--output result.json`. A completed model,
including failed/unverified models, exits zero; malformed input exits 2. No
software is installed implicitly. Missing NumPy prevents the program starting
and must be treated as unavailable evidence, never success.

## Geometry and stated assumptions

The generator manually transcribes the current `src/view/site.ts`,
`src/connectors/bench.ts` and `src/scenarios/beam.ts`; their SHA-256 hashes are
recorded for provenance. Hashing those files does not prove the transcription is
still correct after a geometry change. Such a change requires updating the
fixture and its geometry review.

- Four 3 m posts at X/Y = 0/3 m; bases fix all six DOFs. Columns are split at
  Z = 0, 0.15, 1.7, 2.8, 2.85 and 3 m to retain exact attachment elevations.
- Two longitudinal top rails join Y = 0 to 3 at each X; four uncoupled crossing
  diagonals join Z = 0.15 to 2.85. A crossing has no shared node or connection.
- A single 3 m beam is at Y = 0 (A) or Y = 3 (B), Z = 3.327 m. Its assumed
  centroid follows the scenario reference pose; the detailed body's 20 mm
  centroid offset, shoes and caps are not separate structural components.
  Seats attach at X = 0.09 and 2.91 m through rigid offsets from the head centers
  at Z = 3 m. The seat floor at Z = 3.20 is geometric context, not another support.
- Assumed steel E = 200 GPa, G = E/2.6. Assumed sections: posts RHS180×180×6,
  rails RHS150×170×6, diagonals CHS110×4, beam RHS146×254×5 mm. RHS torsion uses
  the closed thin-wall approximation. These are mechanical hypotheses; visual
  boxes and tubes do not establish real sections or wall thicknesses.
- Beam gravity uses the scenario's 93.3 kg spread over 3 m. Other modeled members
  use section area × assumed 7850 kg/m³ density. Hardware, heads, docking rails,
  arms, cables and gantry self-weight are omitted and load completeness remains
  unverified. This is not reconciled with the scenario fixture inventory mass.
- Column/rail/diagonal intersections are rigid. Temporary seat springs are
  `[1e7, 1e7, 1e7, 2e4, 0, 0]` in global XYZ (N/m, then N m/rad); the nonzero
  X-rotation spring is an explicit **assumed keyed anti-roll capture**, not a
  property inferred from seating. Final springs are `[1e8,1e8,1e8,1e6,1e6,1e6]`.
  The effective beam-center connection includes all seat/head eccentricities as
  one rigid arm; it does not calculate local shoe or head flexibility/stress.

## Loads and stages

The existing `robot-task-guide-three-grip` contact request/result supplies a
representative three-grip wrench distribution for a 102 kg robot/tool assembly.
Its request hash is checked before reuse. The current contact result passes its
declared numerical envelope with 24 included actuator rows. Those capacity
values remain **assumed**, so this does not establish hardware qualification;
the frame records `robot_actuator_limits: assumed` and remains unverified. The frame receives the reported *frame reaction* force and
couple, the negatives of the robot contact wrench, once each. We copy that
representative assembly to X = 0 and X = 3 and translate it to fixture B when
requested. These are prescribed example loads, not freshly solved robot poses
or a stiffness-coupled frame/contact solution.

Every force retains its actual grip point and local applied couple. The solver
maps it to the post node at Z = 1.7 or 2.8 using
`M_node = M_grip + (p_grip - p_node) × F_grip`. This preserves resultant force
and moment without modeling local rails/arms. It does not validate them.

Two sling forces act at X = 0.5/2.5 m and Z = 3.487 m. For an assumed 0.9 m
rise, each vertical force `V` has inward horizontal force `V/0.9`. Their vertical
sum equals the prescribed hoist share of beam weight; horizontal components
induce beam compression. These loads go into the beam once. The equal opposite
hoist/gantry reactions act on another structure and are outside this model.

| Stage | Connection | Hoist weight share |
| --- | --- | --- |
| `temporary-capture` | temporary/keyed anti-roll | 80% |
| `final-joint` | final | 80% |
| `hoist-handoff` | final | 40% |
| `hoist-released` | final | 0% |

These are independent total-load snapshots about an unstressed reference.
Changing stiffness does not carry erection deformation or locked-in stress from
the previous stage. Cables are prescribed forces, not tension-only supports;
seats are bilateral springs. A separate contact calculation must reject uplift,
slip or loss of contact before relying on these snapshots. Dynamics during the
handoff and reverse unfastening sequences are outside this study.

`missing-capture-roll` removes temporary X-rotation restraint and exposes the
beam's torsional mechanism even though its vertical weight can be balanced.
`missing-restraint` removes the bases and exposes rigid-body modes.
`weak-member` supplies an explicitly assumed 1 N m beam bending envelope and
fails it despite other unknown capacities. Merely deleting a diagonal need not
create a mechanism with fully fixed bases; brace counts are not stability proof.

## Model and numerical checks

Each straight prismatic element uses the standard linear Euler–Bernoulli
12×12 stiffness matrix, with local X from node A to B, local Y from the supplied
`local_y` vector projected perpendicular to X, and Z = X × Y. Axial stiffness is
EA/L; torsional stiffness GJ/L; bending uses EIz for local-Y deflection and EIy
for local-Z deflection. Uniform forces use consistent nodal forces and end
moments. End forces are `k_local u_local - f_equivalent`, in A/B node order,
acting on the element ends; internal-section signs need not match those at B.

Global spring DOFs compare B's motion to the rigid-offset motion of A, including
`theta_A × (p_B-p_A)`. Reported `force_on_b_global` and
`force_on_a_at_a_global` are the spring's forces/couples on those nodes.
Supports report ground-on-frame reactions. Free-DOF residuals and the sum of
external and support force/moment about the global origin are checked separately.

Before solving, the restrained stiffness matrix is scaled by a characteristic
length (3 m by default) for translation DOFs. An eigenvalue ≤ 1e-12 of the
largest (absolute floor 1e-10) is a mechanism **or numerically unresolved weak
mode**, not proof of an exact mathematical nullspace. Such cases fail and emit
a diagnostic mode instead of displacements. Positive-definite matrices with
scaled condition number > 1e10 remain unverified without a displacement witness.
This is a stiffness conditioning check, not a modal frequency or buckling check.

Displacements include nodal values and exact constant-uniform-load polynomial
interpolation within each element. Extrema of squared translation/rotation
norms are found at endpoints and real roots of its derivative; this catches a
simply supported beam's maximum deflection even if both end translations vanish.
Member-force envelopes include bending stationary points as well as ends.
The 10 mm displacement and 0.01 rad rotation limits are assumed screening limits.

Capacity input is optional and unknown by default. Each member may declare
positive `limits` for `N,Vy,Vz,T,My,Mz`; connections/supports use global
`Fx,Fy,Fz,Mx,My,Mz`. Capacities are force in N and moment in N m. The conservative
interaction screen sums absolute component-envelope demand/limit. Envelopes
may peak at different points, so this can be conservative. This envelope is
**not** a yield, buckling or design-code interaction equation. A result only
passes it if all limits are present, the sum ≤ 1 and `provenance` is `verified`.
The caller is responsible for establishing that this particular envelope is a
valid conservative capacity model. Assumed/unknown capacities remain unverified;
a known exceeded envelope fails even while other evidence is unknown.

Every physical-fixture result remains **unverified**. Small computed elastic
displacement does not establish capacity, stable cable/contact behavior or a
safe operation. No buckling, P–delta, shear deformation, warping torsion,
plasticity, fatigue, joint/bolt/local rail, foundation/soil or code-compliance
claim is made. Positive linear stiffness cannot rule out compression buckling.

## API, freshness and integration proposal

`frame-request.schema.json` describes the serialized input. The API also checks
references, uniqueness, finite numbers, positive section properties and support
DOFs. A result echoes request ID, world revision, input fingerprint and canonical
SHA-256 of the complete JSON, plus model and NumPy versions.

The fixture deliberately uses the representative contact study's revision 10.
It is **not** bound to visible events `beam-014` (before-revision 13), `beam-015`
(14), `beam-046` (45), or `beam-047` (46). Its output must not be attached to those
events as passed evidence. There is no runtime subprocess or UI adapter here.

A future adapter should regenerate a request from the exact current/proposed
world and bind it to the event's before-revision. Hash all geometry, material,
section, capacity, restraint, joint, load, contact-witness, hoist state and model
version inputs; include validator evidence and stage semantics. Solve the
current supported state **and** proposed released state before committing
`transfer-load`. Recompute/reject after any state mutation. The optional
`transfer_gate` checks revision, fingerprint, exact request hash, model version,
complete stage IDs, an explicit `hoist-released` stage and every stage's status.
`failed`, `unverified`, missing or stale evidence blocks the numerical gate.

A stage name by itself is not proof that the hoist force is zero. The adapter
must derive loads from state and verify the final-stage hoist force/removal,
contact/seat/fastener predicates and all upstream evidence. Results are trusted
local program outputs, not signed tamper-proof attestations. Even a synthetic
`passed` result returns `physical_release_authorized: false`. This numerical
gate is a necessary condition alongside independent contact, local hardware,
foundation, hoist, buckling, geometric and operational checks; it never grants
physical release by itself.

## Validation

The tests independently check cantilever axial extension, both bending planes,
torsion, end moments, uniform-load tip deflection/reactions, simply supported
interior displacement and bending maximum, an oblique rotation of a complete
load/model, eccentric force reduction and rigid-offset spring equilibrium.
Negative tests cover missing supports, missing capture anti-roll, weak-member
capacity, unresolved weak torsion, unknown/assumed capacities, malformed input,
and stale revisions/fingerprints/payload/stage sets. CLI JSON output and
canonical hashing are checked as well.

Reference for the conventional beam/frame vocabulary and broader formulation:
[Frame3DD manual](https://hpgavin.github.io/frame3dd/web/Frame3DD-manual.html).
This implementation is independent, much narrower, and does not run Frame3DD or
claim validation against its complete feature set.
